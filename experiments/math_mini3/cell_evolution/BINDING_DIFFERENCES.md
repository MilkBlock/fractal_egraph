# 35 组 target binding 差异逐组分析

本分析读取已保存的 math6 演化目录，不重新执行 egglog，也不修改运行时。
输入目录和库的 SHA-256、全部 35 组的 pattern ID、变化槽位、构造表达式及
分类结果见 `binding_differences.json`。

## 结论

35 组中，目标模板、原规则输入/常量的相对映射全部相同；目标内部槽位的
相等关系没有组间变化，来源 cell 内部槽位的相等关系也没有组间变化。
差异都涉及目标值与旧上下文的共享关系，不能直接解释为生成了不同的结构。

| 分类（前两行互斥） | 组数 |
|---|---:|
| 目标本地值有时对应旧 cell 的一个端口 | 29 |
| 上述情况，另有 pre 符号在步末归入同一 canonical class | 6 |
| 目标内部别名分区发生变化 | 0 |
| 同时夹杂本地 `new` 编号漂移（与前两行重叠） | 26 |

所有 35 组都含“本地符号 ↔ 旧端口”的差别。这里 `new` 只表示观察器尚未
把该值命名为某个旧端口；不表示它本次刚分配，也不表示它此前不存在。

按规则分布：Add 结合律 9、Mul 结合律 8、乘法分配律 13、减法改写 1、
乘积求导 4。25 组还伴随提交记录差别，10 组只有 binding 差别。

## 实例一：分配律的生成配方没变，接合点不同

目录中的 pattern 292 和 1812 使用相同读取形态：

```text
Add(external_0, external_1) = external_2
Mul(external_3, external_2) = old.port_0
```

目标模板的两个局部量由同一份已 Bake 的代码构造：

```text
u = Mul(external_3, external_0)
v = Mul(external_3, external_1)
```

但两次观测到的槽位落点不同：

```text
pattern 292：u -> new_0，v -> new_1
pattern 1812：u -> new_0，v -> old.port_3
```

两条记录都没有 Math 行插入/更新记录。此处差异不是乘法构造方式不同，而是
步末 v 是否与旧主体的 port_3 对应。旧主体中 port_3 是一个输入槽位；
因此这个例子也说明旧输入可能具有源模板中没有展开的具体结构或等价关系。
现有目录不能区分“此前已经相等”和“该轮其他操作使它们相等”。

## 实例二：26 组含顺序编号噪声

```text
u -> new_0，       v -> new_1
u -> old.port_3，  v -> new_0
```

第二次 u 被命名为旧端口，于是 v 成了第一个匿名本地值，被编号为 0。
`v: new_1 -> new_0` 本身不是另一个结构变化。这 26 组仍有真实的旧端口接合
差异，不能把整组都当作纯命名问题删除。

更稳定的表达是先固定目标模板槽位 `target_slot_3`、`target_slot_4`，再单独
记录它们到当前 canonical class/旧端口的映射。

## 实例三：6 组有跨接口等价信息

例如某个目标根的描述在两个观测间分别为：

```text
post_of = [external_1]
post_of = [external_1, old.port_6]
```

前态编码把 external_1 和 port_6 记为不同值，步末 canonicalization 在后者
把它们对应到了同一个 class。来源 cell 内部 alias 分区没有变化，因为
external_1 不属于来源 cell 的槽位列表；变化跨越了接口。

这是真正需要保留的接合信息，不能只删除多余标签以强行判等。但现有目录
没有足够的 union lineage，不能确定由当前规则、同轮其他规则还是 rebuild
具体促成。它证明了观察到的前后 canonical 对应变化，不提供责任规则证明。

## 对状态机设计的修正

应该拆成三层：

1. **生成配方**：在给定读取条件下确保哪个目标模板存在，以及如何从规则
   输入构造各目标槽位。这 35 组的输入映射和目标配方均未变化。
2. **实例接合映射**：目标槽位落在哪个 canonical class，和哪些已有端口重合。
   35 组的差异应主要存放在这里；6 组的跨接口等价也必须保留。
3. **执行增量**：哪些行实际 Inserted/Updated、哪些本来就有。
   它不是生成配方的种类。

所以，此前“675 种读取形态有多个结果，不能直接做确定性状态机”的表述
需要收窄：640 组只有写入差异；剩下 35 组没有观察到目标内部结构或输入
映射分叉，主要是具体接合方式不同。这并不要求 675 种不同的生成算法。

这不是把所有具体状态判成等价，也不是直接跳过 Join 的正确性证明。
共享构造配方仍需处理真实的 hashcons、union、实例重叠和边界增量通知。
本次仅完成离线分析，没有自动合并模式或改变执行。

## 复现

```sh
python3 tools/bench/analyze_evolution_bindings.py \
  --catalog out/cell-evolution-complete/math-observe/cell-evolution.json \
  --output out/binding-differences.json
```

也可以换成重新采集的同环境目录。脚本检查目标槽位和模板与指定 Bake 库
一致，然后重新分组；它不把 35、29、6 或 26 硬编码为分类条件。
