# Resident Raytrace Pass 3 — 2026-10-30

**Publication remains the dominant cost.** `batched_cell_publish` alone takes
120.847 s in the new encoder diagnostic, 75.28% of summed encoder duration.
The captured dispatch launches **one work item for the whole graph arena**.
This is direct capture/source evidence, not an inference from low occupancy.

This profiles the actual resident ABI7 executor at `167a21b`, after restoring
merge-index continuation, typed seed routing and ordinary RHS execution. It is
not a standalone prototype, and it is not the old hybrid ~12 s backend. The
saved input is deliberately unchanged and **`marker_program` is null**. Generic
Cell recipes and private multi-stage execution are enabled. Do not describe this
as a measurement of the full source-marker → multi-stage Cell pipeline.

Hardware: Apple M3 Max, 40 GPU cores; macOS 27.0; Xcode 27.1 (27A9275).
Machine-readable counters, provenance and checks: [summary JSON](2026-10-30-summary.json).
Offline dashboard: repository `out/resident-profile-20261030/index.html`.

not address this bottleneck.

## Capture limits and retained failures

The captured window is outer command 1353, beginning at completed Run 5795. It
is not one whole logical Run. Capture declares 1 command buffer, 872 encoders
and 864 dispatches. Apple profiles both overlapping and serial replay, embeds
and reloads them successfully; aggregate frame durations are 2476.8453 ms and
2129.6376 ms. These are **diagnostic replay**, not a performance improvement.

However, performance encoder/shader lists are empty; most timeline entries are
`Unknown` or whole-frame placeholders. Consequently **new per-kernel registers,
spill and limiter attribution are unavailable**. They are not filled with the
older 2026-10-26 measurements or zero. Valid command-tree dispatch data is saved
separately. Capture collection success alone is no longer accepted as profiling
success by the skill.

The first direct-exFAT capture crashed `GPUToolsDebugService` in
`DecodeDYMTLDeviceDescriptor`; moving those bytes to APFS did not fix it. The
same window newly captured on APFS was readable. We retain this failure without
declaring the SSD hardware faulty. Capture bundles contain internal symlinks;
the archive helper preserves them in a hash-verified tar rather than relying on
exFAT directory semantics. The verified local capture remains intact.

The initial full timestamp attempt exceeded the device's 32 KiB counter-buffer
limit before producing a measurement. The final adapter uses 16 KiB pages and
checks resolved timestamps against command-buffer time. This failed attempt is
not included in the timing table.

## Reproduce without regenerating code or losing private stages

```sh
S=skills/eggfuse-metal-profile/scripts
R=out/resident-restoration-pass3/pass3-on/program-0/attempt-0
B=out/eggfuse-clean-paths-build
python3 "$S/resident_full.py" --run "$R" --build "$B" --output out/new-full-profile
python3 "$S/resident_window.py" --run "$R" --build "$B" --mode counters \
  --window 1352:5 --window 1888:12 --output out/new-hardware-windows
python3 "$S/dashboard.py" --profile out/new-full-profile/summary.json \
  --hardware out/new-hardware-windows/hardware-summary.json --output out/new-dashboard
```

Prefer reading the saved results to rerunning this unchanged workload. The
original snapshots remain under `out/profile-restored-full-encoder-v2/`,
`out/profile-restored-hardware-summary/` and
`out/restored-publish-apfs-capture/`. Hardware traces/raw exports and the archived
capture reside under `/Volumes/Extreme SSD/eggfuse-profile/`. Raw traces, binary
workers and full graph states are not committed.

No inference-engine optimization is included in this profiling change. The
next controlled experiment should target the serial work inside publication,
while preserving custom merge order. Only after that should we attribute new
speedups to matrix computation, Cell locality or reduced synchronization.
