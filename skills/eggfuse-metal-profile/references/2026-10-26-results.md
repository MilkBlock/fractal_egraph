# Eggfuse Metal profile — 2026-10-26

This profiles the GPU-owned `experiments/device_backend` on the saved real
Raytrace Pass 3 program. It is diagnostic replay, **not a speedup benchmark**.
CPU parsing/extraction and the old CPU-submission assisted matcher are not being
timed here. The backend's pre-existing mismatch with native final graph equality
is not resolved or hidden by these measurements.

Hardware: M3 Max, 40 GPU cores. Xcode/Instruments 27.1. Input SHA-256:
`c727cdf724b020ae585c4051fda36b66576c1ce4252a4d9d59fbb7522d0c7d4f`.
Control: `out/device-prediction-pass3-control`; copied worker only adds labels and
an opt-in one-Run capture. The original program/shader is unchanged.

The full 10,097-Run replay matched saved row counts, logical matches, update flags,
epochs and union counts. Its continuous xctrace was killed while saving and is
excluded. Three bounded windows and a single-Run GPU capture completed instead;
all their executed prefixes passed the same metadata checks. This is not a new
complete-fact/equivalence proof. Failed attempts remain documented in `out`.

| Window | Runs | Target GPU active / span | Compute occupancy mean | GPU bandwidth mean |

Occupancy/bandwidth are Apple's **device-wide** counters, time-weighted over the
target's GPU-active intervals. Other applications may contribute; bandwidth is
the vendor's GPU Bandwidth metric, not a claimed DRAM percentage. Different
counter banks cover slightly different spans. Exact counts/covered seconds are
retained in [summary data](2026-10-26-summary.json). Queue activity is not occupancy.

### RHS: one thread is a concrete limit

The sampled shader timeline attributes 556.9 ms to `commit_effects` in the RHS
window; compute occupancy over those sampled intervals averages about **0.040%**.
Its encoder explicitly launches **one thread**. Source confirms that this thread
loops over all matched bindings, executes RHS actions, then handles deferred
unions. The Run-5776 combined preflight/commit encoder takes about 325.8 ms in
the trace. Do not attribute that combined encoder solely to its first label,
`check_empty_effects`; the shader timeline identifies the long commit work.

`prepare_build` is also a one-thread path; its sampled intervals total 28.7 ms,
with about 0.142% compute occupancy. This is not evidence that all preparation is
serial: the parallel scan/radix/hash kernels are separate.

### Matching: large launch, very little sustained occupancy

Run 9459 (`state-edge-passthrough`) was captured as a `.gputrace` and replayed using
`gpudebug profile run --gpu-state default --exec overlapping`. It has 8 command
buffers, 68 encoders and 62 dispatches. The profile is embedded for reuse.

The `step_21` dispatch launches **698,851 threads**. Xcode lists its duration as
910.8 ms; encoder details report 934.8 ms. These are diagnostic replay fields,
not the original uninstrumented Run time. Its reported properties include:

- Kernel Occupancy **0.54%**, Instruction Throughput Limiter **1.06%**.
- **96 temporary registers**, **48 uniform registers**, **176 spilled bytes**.
- Static shader report: **13,681 instructions**, **920 branches**; FP16 = 0,
  FP32 = 0. The source likewise has no matrix arithmetic on this matching path.
- Xcode sampled **2 of 40 shader cores**. `Cost = 26.31%` is **not** a 26.31%
  elapsed-time share. The corresponding live shader timeline misses much of the
  long encoder duration; interpreting it alone would understate the hotspot.

This supports investigating binding-work imbalance, long dependency chains and
register/private-memory pressure. It does not isolate which is causal; splitting
the work and changing register usage require controlled follow-up experiments.
The six `query_radix_offsets` dispatches each launch only 16 threads; the replay
lists roughly 1.6 ms for several of them. That is another concrete small-width
stage, not evidence that wider unrelated GEMM would help.

### Rebuild: repeated global work and host handshakes

The trace maps command buffers back to actual Runs:

| `context` Run | `rebuild_start` command buffers | GPU-active time in those buffers |
|---|---:|---:|
| 4333 | 157 | 138.2 ms |
| 4335 | **383** | **323.0 ms** |
| 4345 | 314 | 275.0 ms |

Worker source submits one such buffer per rebuild-loop iteration and waits for
completion before reading its continuation flags. The main-thread CPU profile,
restricted to the observed GPU span, has **283 / 301 samples (94.0%)** containing
`waitUntilCompleted`, with `__psynch_cvwait` at the leaf. This is a sample
proportion, not exact wall time. The tool labels these samples `Running`; the
actual stack identifies the wait.

Rebuild has substantially greater occupancy and bandwidth than the matching
window. Its sampled shader time is led by `rebuild_insert`, `rebuild_assign`,
`rebuild_canonical`, `merge_offsets` and `merge_scan`. Priorities are reducing
unnecessary global passes and handshakes, then improving access/scan layout—not
assuming this phase has the same limitation as the serial RHS.

## Follow-up priority

1. Partition independent RHS effects and preserve required merge/subsume order.
2. Avoid hundreds of global rebuild iterations and per-iteration host waits.
3. Split long matching work; test register/private-array reductions and work
   balancing on the identified `state-edge-passthrough` kernel.
4. Widen genuinely serial scan/offset stages and batch tiny dispatches when
   dependency/Run boundaries permit.

These are proposals, not implemented performance claims. A 2× speedup or
"Metal fully utilized" result has not been established.
