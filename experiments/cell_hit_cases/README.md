# Raytrace Pass 3：Cell 到底命中了什么

结论：之前的收益主要来自固定根节点接线、依赖订阅、局部数学证明，以及整段查询接管。**并不是每个 Cell 都有很高的缓存命中率。** 本次记录的端口缓存率为 **14.06%**（515,238 次缓存读 / 3,665,110 次端口读）。

实际运行时没有具体闭包目录条目；这里的“每个 Cell”按 **31 个已安装的参数化 Cell 程序**统计：17 个 scalar 查询程序、14 个 terms/helper 程序。它不是 Analyze 库中每个 RipSat e-class 的覆盖率，也没有记录每个运行时实例的独立命中历史。

## 口径

后续归因修正：本报告统计执行程序和缓存，并非 Cell credit。空表短路、固定查询计划及普通取值应保留在共同基线，不能因程序名叫 Cell 就领功。[新的证明组消融](../cell_credit/README.md)只关闭语义证明，保留这些公共工作。

- **端口缓存率**：缓存读 / (缓存读 + 新索引读)。包括复用“该键仍缺失”的结论；不包括最初的根查找，不是物理内存命中率。
- **非空回答率**：非空 Cell 查询回答次数 / Cell 查询请求次数。空回答也可能很有用。
- **查询接管率**：Cell 完整回答次数 / 该规则全部请求次数。这 17 条规则均为 100%，但不能称为缓存命中率或整个工作负载覆盖率。
- **复用起点率**另存 JSON/CSV：至少复用一个端口的评估次数 / 所有 dirty-seed 评估次数。它与每次读取的缓存率不同。
- 无端口读取的项目标为 `—`。缓存 0% 意味着读过但没复用；`—` 可能是没有实例、叶子无需读取端口，或被更高层证明替代。
- GPU 行访问移除指这条查询不再在 GPU 上执行的工作；CPU 仍需处理依赖、取值和 effect，不能把移除数当作零成本或单项时间加速比。

## Case 1：If 确实复用了未变化的兄弟输入

```egg
(rule ((= expr (If pred inputs then else))
       (= sum (+ (Expr-size inputs)
                 (+ (Expr-size else) (+ (Expr-size then) (Expr-size pred))))))
      ((set (Expr-size expr) (+ sum 1))) :ruleset always-run)
```

固定接线是一个 If 根加四个 size 输入。若只有 else 的 size 变了，订阅知道应该唤醒哪些 If；其余未改变的输入可以继续使用。

本次：13,607 次根评估，13,016 次至少复用一个端口（95.66%）；实际端口读中 32,701 次缓存、20,035 次新查（62.01%）。这两个百分比不能混用。最终有 12,946 个完整增量 binding；根评估、结构候选和最终 binding 不等量。

历史对照中，这条规则有 4,487,242 个 GPU 起点和 1,624,328 次活候选行访问。它的接管收益同时来自减少起点、固定接线和缓存，不只是最后的 62.01%。

## Case 2：Get 缓存 0%，仍然消掉整条查询

```egg
(rule ((= expr (Get tup i)) (= sum (Expr-size tup)))
      ((set (Expr-size expr) sum)) :ruleset always-run)
```

它只有一个 size 端口。被该端口的更新唤醒时，并没有另外几个未变化的兄弟输入可复用；根因 union/rebuild 改变时也会重建路径。

本次 994,600 次根评估，977,455 次新端口读取，缓存读取 **0**。但它直接沿 Get→tup→size 的固定路径读取，产生与原查询相同的 957,751 个 binding，移除了 GPU 的 1,234,556 次候选行访问。因此“缓存命中率高”不是此前收益的必要条件。数据没有把每次零命中的原因逐一分桶，上述是由代码机制支持的解释。

## Case 3：没有 Switch/Cons，也能省工作

本次 Switch、Cons 两个 scalar 模板的根评估数都是 0，1,798 次请求全部回答空。没有命中任何具体实例，也没有缓存读。

然而历史 GPU 对照分别启动了 2,243,450 和 1,121,725 个起点：其它 atom（例如 size 表）的增量也能启动查询。实际计数为 `refuted_seeds=0`，全部起点进入第一层 Join 后取到空结果：Switch 的 depth-1 entries 为 2,243,450，Cons 为 1,121,725，两者的 live_rows 均为 0。此前将退出归因为“起点 refutation”是错误的。Cell 根索引及订阅避免了这些起点与空 Join 探测。

这是“知道没有根、提前回答空”的收益，不能包装成 Bake 命中了大量闭包。这里的对照是本项目的通用 GPU 查询后端，不是 pristine egglog 的空表处理能力。对必需的正向 LHS 表做通用空表短路也能避免这些起点；因此它是 Cell 服务当前顺带取得的通用调度收益，不是 Cell 独有的闭包收益。

当前 Cell 程序同步原生事件后，只处理待唤醒的根。没有 Switch 根时，也没有依赖其 size 输入的订阅，所以 size 表更新不会唤醒它。查询服务仍每次返回完整的空增量结果，再由 `table_live` 将该查询从 GPU 待办中移除。后来出现 Switch 根时，原生事件会把它加入待处理集合；首次读取会查已有输入，缺失输入也会注册订阅，不会永久跳过这条规则。

## Case 4：候选结果改善程序移除的 GPU 行访问最多，缓存只有 9.45%

```egg
(rule ((PotentialExtractedExpr expr (TCPair term cost))
       (= (ExtractedExpr expr) (TCPair oldterm oldcost))
       (< cost oldcost))
      ((set (ExtractedExpr expr) (TCPair term cost))) :ruleset terms-helpers)
```

固定入口是具体候选，再按 expr 找当前结果，读取两侧 cost。它维护实际读取的依赖，保留多别名分支，并将原生 set/merge/rebuild 交回 egglog。

端口缓存为 56,030 / (56,030 + 536,749) = **9.45%**；仍移除了 **9,269,688 次 GPU 候选行访问**，占整个 Cell 关闭/开启差值的约 37.5%。

此外，当前联合范围证明候选代价固定、最佳代价只会下降：若候选已经不能改善结果，在该饱和范围内就可以暂时停止重查。本次累计记录 73,607 次这种退役，跨边界可以重复计数。边界退出或外部更新会恢复相应检查。这个数学证明与普通端口缓存也是两种收益。

## Case 5：整块闭包宏和内部比较闭包必须分开

- 12 个外层联合边界，fresh-DAG 整块闭包宏命中 **0**；全部使用参数化 dataflow。
- 12 个边界均通过 uniform-cost 范围检查。在这个范围内，TCPair 的同一等价类中的所有 Term 别名具有相同 cost。
- 内部 Smaller 饱和证明执行 1,185 次，可直接比较 cost 并传播等价请求，而无需反复枚举 Term 别名。584 次未造成原生变化。
- 对应的三条普通比较程序没有执行，故其缓存率是 `—`。89,226 是 union 提议数，不是新增事实或有效 union 数。

当前报告没有记录“所有可能的内部比较证明尝试”这一通用分母，因此不伪造一个全局闭包命中百分比。

## 来源、验证和复现

这次仅补跑一次实际完整 Pass 3 的诊断，未重跑性能对照。新增统计没有改变规则、调度、匹配算法或 native effects；完整图检查通过，逐规则起点、产出、Cell 回答与历史开启组一致。

- 新诊断：`out/cell-case-telemetry`，telemetry v2 首次包含全部 31 个程序、新索引读分母和非空回答计数。
- 历史同二进制工作量对照：`out/join-depth-final-s0r1` / `out/join-depth-final-s1r1`；两组均开启原有 refutation，区别是 CPU Cell 服务关闭/开启。
- 24,717,514 次 GPU 活行访问差值中，表内程序合计 24,638,350 次，其余规则净变化为 79,164 次；保留这个差额，不把它强塞给某个 Cell。
- 所有行都是真实运行时计数，但插桩秒数不是速度证据。这里没有得出每个 Cell 的独立耗时贡献。
- 当前来源是固定参数化 Cell 程序与范围证明，并未证明任意 Analyze/Bake 库的每个 RipSatCell 都具有这样的命中率。
