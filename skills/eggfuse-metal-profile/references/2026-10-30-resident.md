# Resident ABI7 capture adapter

Validated on the actual `generic_cell.swift` runtime, M3 Max, Xcode 27.1
(27A9275). No old DVB6/7 protocol or whole-prefix replay is involved.

- A saved chain checkpoint after Run 1 was restored in fresh processes.
- Captured and ordinary executions performed exactly Run 2.
- Complete rows, identities, values, visibility, stage history, and counters agree.
- The trace contains one command buffer and eight encoders: a dispatch-clear
  blit plus prepare, match, pack, evaluate, publish and two fingerprint phases.
- The source phase encoders are split only for capture attribution. Do not use
  this timing as the production speedup or as a Pass-3 hotspot estimate.
- All checkpoint regression cases still pass with the capture-capable worker.
- Eight existing profiling script tests pass.

Artifacts are on the user-provided external disk:
`/Volumes/Extreme SSD/eggfuse-profile/20261030-resident-chain/`.
The capture is `run.gputrace`; `provenance.json` records the exact source, worker,
checkpoint and reference. `analysis-final/summary.json` successfully reads the
embedded Apple profile, including real encoder durations and shader properties.

Tool repair: Xcode 27.1 reported successful collection but left the collecting
session's performance tree empty. Loading again there said "already loaded".
Embedding the result, closing that session, and loading it in a **new** session
exposes all eight encoders. The script now uses that sequence. It also no longer
asks the performance directory for an unsupported `info` handler or embeds an
already embedded session twice. Failed attempts remain in the artifact directory;
empty results were never interpreted as zero GPU work.

The new adapter covers capture/replay. Its xctrace counters and CPU-wait adapter
is not implemented yet; the historical worker adapter retains those facilities.

A full-source Pass-3 physical checkpoint also exists after Run 20 at
`/Volumes/Extreme SSD/eggfuse-profile/pass3-run20/checkpoint`. It has 13,935 rows
and ends in `type-helpers`. This is an unfinished prefix, **not** a completed
Pass-3 result. Initial Metal shader compilation took 297.98 s; the next process
took 34.24 s to load/compile pipelines, while those first 20 Runs used 0.191 s
GPU time. Setup and inference must remain separate.

The real Pass-3 **Run 21** (`type-helpers`) was then captured directly from that
checkpoint. It produced four logical match bindings and ended at 13,939 rows.
Capture and ordinary fresh-process replay have identical full state and history.
Files are in `/Volumes/Extreme SSD/eggfuse-profile/20261030-pass3-run21/`.
This validates the new adapter on the actual source, not only the chain fixture.
It is an early diagnostic Run, not a claim to have found the full-run hotspot.

Another bottleneck is explicit in these records: capture shader compilation was
340.32 s and ordinary restart compilation was 314.50 s. The latter's actual GPU
execution was 89 ms. The monolithic generated shader/pipeline preparation needs
persistent compilation caching before repeated one-Run diagnostics become cheap.
These setup seconds must not be attributed to GPU inference or the disk snapshot.

Apple hardware-profile collection on this full-program capture **did not finish**:
`analysis/collection.txt` records the attempt; the 300-second replay timeout fired
while MTLCompilerService was compiling (approximately one busy CPU core). The own
gpudebug session was closed; the capture and exact replay results remain intact.
There are no real Pass-3 occupancy/limiter results from this attempt, and no retry
was performed. `capture_report.py --timeout-seconds` now makes an intentionally
longer replay explicit; the immediate engineering problem is compilation caching,
not increasing inference limits or silently re-running the full schedule.
