# 价值验证：动态 Zobrist 与共享模板存储

已实现可执行原型并完成测量。**证明了一个有条件的价值：重复局部结构可以显著减少实际存储分配，Zobrist 增量更新可以减少维护指纹的成本；但它不是免费优化，也没有证明整个 egglog 的 RSS 已经下降。**

## 测到的收益和代价

以下是优化构建、独立进程、随机执行顺序、3 次测量的中位数。内存为压紧容量后实际保留的 Rust 分配请求字节，包含模板、绑定、引用、哈希桶、字典、class 元数据；不是估算的文件压缩率。

| 数据 | 原始存储 | 共享＋增量 Zobrist | 净内存变化 | 更新相对原始存储 |
|---|---:|---:|---:|---:|
| 普通算术，32,768 个实例 | 1.867 MiB | 1.258 MiB | **减少 32.6%** | 慢 2.09 倍 |
| 四元求和，32,768 个实例，每个 24 个节点 | 15.906 MiB | 1.407 MiB | **减少 91.2%** | 慢 3.11 倍 |
| 六元求和，1,024 个实例，每个 720 个节点 | 19.716 MiB | 0.058 MiB | **减少 99.7%** | 慢 1.89 倍 |
| 低重复负对照，16,384 个实例 | 3.953 MiB | 4.109 MiB | **增加 4.0%** | 慢 6.82 倍 |

进程级峰值 RSS 也下降：四元数据约 26.5 → 4.2 MiB；六元约 46.0 → 2.05 MiB。这里是独立存储实验进程，**不是 egglog 引擎进程**。RSS 包含分配器、缓冲区等影响，不能与保留分配量混为一谈。

## Zobrist 自身贡献了什么

共享模板和 Zobrist 是两个不同的收益来源，所以比较了两个使用相同存储、同一种指纹、同样精确比较的实现：

| 六元数据 | 每次全量重算 Zobrist | 增量 XOR |
|---|---:|---:|
| 更新阶段耗时 | 0.313 s | **0.166 s** |
| 计算的元素 hash 数 | 265,789,440 | **737,280** |
| 最终存储 | 0.058 MiB | 0.058 MiB |

因此：**内存收益来自模板共享；Zobrist 增量维护在这个案例上将更新阶段加速约 1.89 倍。** 它没有把精确比较、端口处理和写时复制的成本变成零，因此整体更新仍比未压缩的紧凑存储慢。

四元数据中的同一增量优化约为 1.13 倍；普通小 e-class 约为 1.01 倍，基本没有明显时间收益。端到端时间还包含输入流读取等成本，详见原始结果，不能把更新阶段加速当作整个推理加速。

只加检测、不替换原始存储的对照也测了：四元数据从 15.906 增至 17.157 MiB。这个版本保留原始数据和完整候选检测结构，证明该具体旁路实现只加开销；不声称所有检测器都需要这么多内存。

## 为什么能省内存

六元案例的每个 e-class 保存同一组 720 种排列，但各实例的 child ID 不同，普通具体节点去重不能把它们视为同一个节点集合。

原始存储每个节点是 7 个 u32（operator/arity 头＋6 个 children），每个实例的节点数据需要 `720 × 28 = 20,160` 字节。

共享版本保留一份 720 个 u64 的模板，每个实例保存 6 个 u32 的 child 绑定和模板引用。共享表示仍能逐节点还原实际 child ID；没有合并这些实例的 e-class，也没有丢弃节点。

## 实验流程

1. 用本地 egglog 实际执行求和旋转、相邻交换规则，分别饱和到 24/720 种排列。普通算术来自已有真实执行快照。
2. 对每个实例的相邻快照产生插入、删除和 root-ID 更新事件，并额外注入重复插入来检查集合语义。
3. 将相同事件流输入四个实现：紧凑原始存储、原始＋检测、共享＋全量重算、共享＋增量 XOR。
4. 扩大规模时重复已有历史并重命名为互不混淆的实际 ID。这不是同规模独立运行 egglog 得到的生产数据。
5. 低重复负对照是随机六参数节点集合，明确属于合成数据，没有伪装成真实 rewrite 工作负载。

端口在新节点到达时按首次出现顺序分配，不预先知道未来节点，不运行穷举同构算法。这样的绑定能错过发现顺序不同的同构模式，但不会导致错误共享。旧端口绑定仍保留，计入内存。无人引用的旧模板会立即回收。

## 正确性

- 对未放大的全部数据流，各实现共做了 **7,920 次完整快照逐项比较**。
- 大规模运行的变更数量及完整扫描校验和在各实现之间一致。
- 4 项 Rust 测试覆盖重复插入、删除、写时复制、在线绑定、canonicalization 风格的去重，以及全量和增量指纹一致性。
- 其中一个测试强制 hash 为 **0 bit**，让所有同大小集合发生碰撞，再运行 **4,000 次差分更新**。精确结构比较保持结果正确。

## 边界与下一步判断

这是一套可更新、可扫描的**局部节点存储原型**，不是整个 e-graph 引擎。输入来自快照差分，因此测量不包括在 egglog 提交路径上识别真实增删的开销，也不包括原有 query indexes、union-find、时间戳、subsumption 和外部 child 内容。

Sum4/Sum6 是人为选择的高重复案例，用于证明收益存在，不代表一般编译器负载。对这种纯交换律例子，直接规范化交换算子可能比枚举后压缩更好；本实验没有证明胜过这种语义专用方案。

结果支持只对收益足够大的重复区域启用共享，并优先考虑稳定区域、批量压缩以及复用模板变更，而不是所有小 class 都立即压缩。能否让整体 egglog 更省内存且速度可接受，仍需真正替换表存储并连同索引一起测量。

## 复现

在仓库根目录执行：

```sh
cargo run --bin zobrist_corpus -- results/zobrist_storage/permutation_snapshots.jsonl
cargo test --lib
cargo build --release --bin zobrist_storage
python3 experiments/zobrist_storage/run.py
```

Python 只依赖标准库。完整报告在 `results/zobrist_storage/report.md`，每次独立运行的数据在 `runs.json`，汇总在 `summary.json`；生成的二进制事件流已有局部 `.gitignore`，不会默认加入版本控制。
