# 浅层 marker：改变匹配坐标，同时核算维护成本

独立 CPU 向量原型。沿用四条 math rewrite、两个参数模板、八个输入实例及因式提取边界。
marker 是统一向量状态中的额外通道，**没有修改生产 egglog 的 sort/rule，也没有 GPU 内核**。

```text
T0 = p0*(p1+p2)
T1 = T0 + p0*p3
```

## 1. 如何增加浅层信息

16 维 Hadamard 输入编码满足 `h(a)·h(b)=16[a=b]`。新增两种线性 marker：

```text
M12  = h(p1) + h(p2)
M123 = M12 + h(p3)
```

若每个实例内输入互异，两个含 m 个输入的 marker 的点积是 `16 × 交集大小`。
点积恰为 `16m` 等价于整个输入集合相同。没有随机误差或模糊阈值。

- Pair 策略：把内层 Add 的无序 pair 暴露到深度 0。
- Whole 策略：也保存 Pair，但对三叶因子优先读取全部叶子的 marker，再检查外层角色。

Pair marker 相等足以判断二叶 Add 相等；三叶 Whole marker **不**足以判断树相等。

```text
(a+b)+c vs (a+c)+b：全叶集合相同，内层 pair 不同，必须保留外层检查。
(a+b)+c vs (a+b)+d：内层 pair 相同，外层不同，Pair 策略必须继续检查。
```

因此两种浅层读取信号没有无条件的强弱关系。Whole 状态包含更多信息，但本次明确的
读取策略未必更好；它也可以选择只读 Pair，不过仍然支付新增通道的维护与存储成本。

这不是原 TPR 内积的低秩线性分解，而是**针对交换律等价性的编码＋精确判定**。
完整输入编码没有删除，输出 binding 仍可从原端口恢复。

## 2. marker 从哪里来

`MarkerPlan` 扫描 Bake 输出的所有 Mul(k,u) 接口表达式，自动找到 k 中的 Add 子结构。
按符号输入 support 去重，生成 marker 支持集、加法依赖和接线描述。

构造只需要已有输入向量相加，不重新匹配 constructor，不查原图。
同一模板的多个触点共用 marker；同形 marker 使用共同的物理向量布局。

当前仅证明 Input、Add(Input,Input)、Add(Add(Input,Input),Input) 这些接口形状。
其他结构、重复输入及任意动态 union 不在本次保证范围内。

## 3. 公平对照

新调度器在每个批次执行前再次查看共享证据，可以消掉前一批次已经算过的条件。
为避免把这项改进算到 marker 头上，保留三个层次：

1. 上一版逐层实现；
2. 相同新调度器，但不添加 marker；
3. 相同新调度器，添加 Pair 或 Whole marker。

### root-only

| 方案 | 匹配乘加 | 矩阵批次 | 冷启动 marker 加法 | 新增数值槽位 |
| --- | ---: | ---: | ---: | ---: |
| 原逐层 | 1,568 | 10 | 0 | 0 |
| 相同调度，无 marker | 1,568 | 10 | 0 | 0 |
| Pair | 1,088 | 4 | 128 | 128 |
| Whole，优先读全叶 marker | 1,136 | 4 | 192 | 256（含 64 padding） |

Pair 比公平基线少 480 次匹配乘加，但必须计入 128 次构造加法、额外状态和维护。
普通加法与乘加分开列出，不把它们当成相同时间单位；尚不能声称端到端加速。

Pair 的 frontier：

```text
Bake：完成16 / 排除160 / 未知80
深度0：完成36 / 排除218 / 未知2
深度1：完成38 / 排除218 / 未知0
```

Whole 在深度0还留下4个未知，其中包含全叶集合相同但括号不同的负例；深度1正确排除。

### 全部内部触点

| 方案 | 匹配乘加 | 矩阵批次 |
| --- | ---: | ---: |
| 上一版逐层 | 9,504 | 16 |
| 相同调度，无 marker | 8,736 | 16 |
| Pair | 8,736 | 16 |
| Whole | 8,736 | 16 |

这组数据中 marker 没有额外矩阵收益，首次创建仍要付出加法和状态成本。
不能将 9,504→8,736 的纯调度收益归因于 marker。

## 4. 复用已有证据，而不是重复检查 marker

当 Input 比较已得到足够结果，可以直接证明两个 marker 集合相同／不同，不再运行
marker 矩阵。证明使用编译好的叶子置换，保持完整的对应关系；未知不当作失败。

对于全部内部触点，Pair 推出了 28 个 marker 条件，Whole 推出了 34 个。
这种推断也有 CPU 成本，报告记录推断尝试、叶子证据读取和全部 evidence reads。

marker 同形批次按支持大小、相对槽位、源模板对组织。先计算原子条件，然后根据已有
证据决定是否还需要 marker 批次。未请求位置、重算条件和输入矩阵规模也计数。

## 5. 增量维护

`update` 接受明确的输入事件：保留哪些旧输入、哪个位置得到新码字。
不通过查图重新发现变化，不假设任意 union 都能如此更新。

T0→T1 的已知 graft 保留 p0/p1/p2，追加 p3：

| 方案 | T1 从头构造加法 | 从 T0 接续加法 | 直接保留 |
| --- | ---: | ---: | --- |
| Pair | 16 | 0 | 原 M12 对象 |
| Whole | 32 | 16 | 原 M12 对象 |

测试同时检查数值相等和对象共享。原生 `Sat(T0)+graft` 与从头 `Sat(T1)` 的完整
constructor 行／等价分区一致，为 22 个 e-node / 11 个 e-class。

其他受支持的参数替换：

- 改 p0：Pair/Whole marker 都不变；
- 改 p3：Pair 不变，Whole 只更新 M123（16 次加法）；
- 改 p1：更新 M12（16 次）；Whole 再由新 M12 更新 M123（再16次）。

输入码字验证、别名检查、对象分配及调度并不免费。报告额外记录码字分量检查；上表的
零只指 marker 加法为零，不是整个更新零开销。参数替换实验代表新实例的数值维护，
不能解释为任意非单调图更新或全局 union 的完整维护机制。

## 6. 正确性与复现

全部方案在 root 和全触点两种模式下输出完全一致；462 条带触点标签的 binding 与
native 相同，全局去重110条。原始规则目标检查通过。
新增测试覆盖两个方向的不足信息反例、依赖更新、别名拒绝、调度收益归因，以及禁止
旧 matcher／constructor 查询时 marker 构造、维护与匹配仍正常完成。

```sh
python3 experiments/cell_spine/marker_context/demo.py \
  --output out/marker-context-next

# 已编译 native 工具时可加 --skip-build。
python3 -m unittest experiments.cell_spine.marker_context.test_demo -v
```

输出目录必须不存在，默认离线构建。Python 仅用标准库。
`index.html` 给出两种 marker、完整成本、增量维护与三态进展。
`report.json` 保留完整计数和状态快照；提交的 `results.json` 只保留摘要。
同一份构造好的 marker 状态用于两种查询模式，构造成本不在实际运行中重复支付；
两张表的冷启动列表示各自作为首个查询工作负载时需要计入的成本。
