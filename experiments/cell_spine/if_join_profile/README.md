# 为什么稀疏 If 的新 marker 反而更慢

**主要时间花在两条没有成功 match 的继承规则上。** 新表示减少了 LHS
读取项，却使 Join 更早尝试 `Cell × 外部条件` 的组合，再检查真正把二者
关联起来的分支、上下文和活跃 Summary。更短的查询不等于更窄的搜索。

输入沿用上次 bench：1,000 个 If，其中 min/max 各 50 个，900 个不匹配。
库、输入和规则顺序冻结，没有重新 Bake 或重跑 Gurobi。所有变体都完整
导出并验证 **16,208 个 e-node / 14,108 个 e-class** 的双射等价关系。

## 先按规则找出时间在哪里

| 规则 | 旧表示 search/apply | 新表示 search/apply | 成功 match |
|---|---:|---:|---:|
| `impl_6_5_cover_5` | 1.502 ms | 32.887 ms | 0 |
| `impl_7_5_cover_10` | 0.319 ms | 31.910 ms | 0 |
| 合计 | **1.821 ms** | **64.797 ms** | **0** |

它们是小 Cell 的消费者被大 Cell 接管之后生成的规则：用大 Cell 的
Summary 代替一部分原始输入，再与外部 If 及另一个活跃 Summary 连接。
本输入没有满足这些组合的地方。规则仍可能在其他输入或后续增量交互中
有用，不能因为这一次 match 为零就永久删除。

## 实际进入了哪些 Join 阶段

旧 marker 读取 canonical seed 来还原参数。这些查询虽然更长，也把
Cell 内部节点的关系显式留在 Join 里。新 marker 直接携带更多参数，删除了
解码查询，查询图和分解方案随之改变。

原生计划把查询拆成若干段：每段保留部分绑定供下一段使用。新计划第一段
包含以下阶段；下表统计的是**实际进入次数**，不是静态计划顺序：

| 新计划第一段的阶段 | 两条规则各自的进入次数 |
|---|---:|
| Summary 分支值与 Get/Single 的连接 | 1 |
| Bop 条件与 If/InIf 的连接 | 50 |
| Summary 中的 operator 与 Bop operator 的连接 | 50 |
| 第一个 Get 结果与 Bop 第一个操作数的连接 | **50,000** |
| 第二个 Get 结果与 Bop 第二个操作数的连接 | **50,000** |
| If 分支与 Single 的连接 | **50,000** |

这里有 50 个活跃 `Spine-Summary-1`，以及 1,000 条原始 Bop 条件。
这与阶段计数中的 `50 × 1000 = 50,000` 对应：先绑定 Cell 的分支值，
仍然会为它考虑大量外部条件。后面的连接才排除不属于同一合法组合的项。
第一条规则还需要下一段检查另一个活跃 Summary；没有留下完整匹配。

```text
50 个 Cell 的分支值
       │
       ├─ 各自尝试 1,000 个外部条件
       │
       ▼
50,000 次操作数、分支等局部查询
       │
       ▼
补齐上下文与其余活跃 Summary 的条件
       │
       ▼
0 个完整 match
```

**这不是说存了一张 50,000 行的中间表。** 第一段最终保留的部分绑定，
两条规则分别只有 **50 行和 0 行**。贵的是保留这些结果之前已经做完的
大量失败搜索。

| 规则 | 旧表示候选行访问 | 新表示候选行访问 |
|---|---:|---:|
| `impl_6_5_cover_5` | 78,650 | 501,350 |
| `impl_7_5_cover_10` | 1,250 | 500,250 |
| 合计 | **79,900** | **1,001,600** |

候选行是各阶段访问次数之和，不是不同的逻辑匹配数。原始记录见
`blocks.csv`；`hot_plans.json` 保存了两端最贵查询的完整原生计划。
编译后的阶段列表不等于运行时固定顺序：本次计数是在动态排序之后记录的。

另用同一冻结库做了 100 个 If 的规模对照。该例有 5 个对应 Cell、100 个
外部条件，操作数阶段各进入 **500 次**；扩大到 1,000 个 If 后，这些阶段
进入 **50,000 次**。输入扩大十倍，相关阶段的尝试次数扩大一百倍，符合
这里的两组绑定相乘，而不是每次查询固定开销稍微增加。100 个 If 的完整
图也通过判等；数据见 `scale_100.json`。这不声称所有规模/计划都遵守相同
复杂度，规划器还有随规模变化的分支。

## 两个反事实对照

| 变体 | 整个推理阶段 | search/apply | merge | rebuild | 候选行访问 |
|---|---:|---:|---:|---:|---:|
| 旧表示 | 50.334 ms | 30.503 ms | 1.578 ms | 15.988 ms | 913,354 |
| 新表示 | 100.948 ms | 83.136 ms | 1.866 ms | 14.602 ms | 1,276,552 |
| 新表示，仅把两处 Single 读取改回 canonical 表 | 107.864 ms | 84.932 ms | 1.908 ms | 19.448 ms | 1,276,552 |
| 新表示，诊断性移除两条热点规则 | **37.213 ms** | **18.415 ms** | 1.570 ms | 16.068 ms | **274,952** |

第一项反事实推翻了最初的一个猜想：原始表/canonical 表的选择本身不是
主要原因，改回后查询计数完全相同。第二项反事实确认两条规则是主要热点。
两项对照在这个输入上都通过全图判等、保持 2,200 次逻辑 match。

本次没有把这两项反事实装进生产编译器。删除未命中规则不具有跨输入的
正确性保证；替换表名也没有被当作通用改写。没有更改 Gurobi 权重。

## 成本模型缺的是什么

它目前奖励较少的读取项，没有计算查询分解后、关键关联条件生效前的
绑定数量。哪怕用成功 match 的频率加权，也会把这两条规则算作零成本。
因此只看成功的 rule-apply 历史，会漏掉这次最贵的工作。需要补充的是
未完成匹配的 Join 前缀统计，本次没有为此保存完整失败 binding 历史。

下一步应评估的是：Cell 的边界值能否早期确定外部 If 的位置，还是仅凭
共享 operator 就去尝试一批外部条件。应保留能限制绑定范围的关系，或把
这种边界连接编成适当的 fragment；不能只删除看起来冗余的解码原子。
本次已经测出问题所在，但没有声称找到了通用的最优规划方法。

## bench 新增能力与复现

原生已有报告能提供逐规则耗时和编译计划，但逐阶段候选统计没有实际填数。
这次加入了一个**默认不编译**的 `native-join-work-profile` 功能：

- 对指定规则记录查询段的计时、探针计数差额、保留的部分绑定行数。
- 对实际执行的阶段记录进入次数；没有每行计时，也没有记录逐条绑定历史。
- 只允许单线程，因为原有探针计数器是全局的。并行时明确拒绝归因。
- 不改变计划、调度、规则或事实；普通构建不包含这些新钩子。

```sh
# 使用已有冻结输入，不重新 Bake；脚本默认构建诊断版本。
out/cell-spine-venv/bin/python tools/bench/if_join_profile.py \
  --ablation-root out/spine-joint-ablation --output out/if-profile-new

# 较小输入的单次规模对照，继续复用同一库。
out/cell-spine-venv/bin/python tools/bench/if_join_profile.py \
  --ablation-root out/spine-joint-ablation --output out/if-profile-100-new --ifs 100 --skip-build

# 开关、计数和完整图一致性测试
EGG_LAYOUT_TEST_JOIN_PROFILE=1 out/cell-spine-venv/bin/python -m unittest discover \
  -s tools/bench -p test_if_join_profile.py -v
```

没有上述输入目录时，先按 `../joint_runtime/README.md` 生成原始消融结果。
诊断版需要复现默认构建时，可不带 feature 重新构建原生 runner。

`summary.json` 包含本次二进制哈希、完整图判等和全部分段记录；`rules.csv`
包含所有规则，包括零 match 的规则。`blocks.csv` 中的 plan 行已经包含子段，
不要将二者再次相加。第一段保留的行也不是最终 match。

所有时间来自单次诊断运行。查询计划、块级时钟和阶段计数都有开销；
它们用来归因，不是无插桩性能基准。对照仍为同一修改版内核，不是 pristine。
默认内核先前已有无条件 atomic 探针计数器，本次没有把它们当作免费开销。
目前没有将单次索引构造和单次筛选各自计到纳秒；已经确认的是这些阶段
的执行次数暴增，以及两条规则对整体耗时的影响。不能把块级总时间除以
任意一个计数，当作单次操作耗时。
