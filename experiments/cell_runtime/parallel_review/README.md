# Cell CPU 瘦身顺序与并发评估

2026-11-03，评估版本 `a5e3e9a`。建议采用 **Recipe/有序提交核心 → 编译共享入口 → 可选残余过滤 → 重 Run 只读并行** 的顺序。首个主线候选使用普通表存储、默认启用的有序 merge 程序与编译共享入口。跨阶段 Spine 和引用视图各有用途，应分别验收。此次交付是架构评估、实验与迁移方案，运行时默认配置维持评估版本的设置。

## 为什么要拆开合并

测试使用同一份 sum-bits Pass 3 marked 程序、同一个单线程 Cell release 二进制，每个矩阵按四个交错次序各跑一遍。下表为推理时间中位数及确定性的检查次数。每行的对照只在所在矩阵内成立。源码改写、Bake、进程启动、导出、整图审计均在推理时间外。

| 同矩阵的选择 | 推理 ms | 匹配及入口候选检查 |
|---|---:|---:|
| 公共路径，copied marker + absorption，默认 merge 程序 | 125.40 | 86,432 |
| 公共路径 + 编译共享入口 | **114.46** | **25,643** |
| 公共路径 + 跨阶段 Spine、部分接续、共享检查及 receipt | 154.13 | 34,279 |
| 公共路径 + 两组功能 | 142.63 | 25,643 |

共享入口单独开启使时间下降 8.72%，检查减少 70.33%。在已有共享入口上叠加 Spine，多花 28.17 ms。后一种配置确实接续了 3,775 个绑定，精确键查找从 62,212 降到 61,341，查询行解码从 53,648 降到 50,847，最终候选数相同。另一次分阶段计时中，这两条路径的发布阶段分别为 5.78 和 19.75 ms。这解释了为什么按新增能力或命中数决定合并优先级会选错。以上两个关键切换各通过 1,497 个完整图、绑定和调度快照。

| 存储矩阵，关闭跨阶段 Spine | 逐规则入口 ms | 共享节点 ms |
|---|---:|---:|
| 普通存储 | 127.27 | **111.50** |
| 复制 marker 字段并允许吸收 | 138.22 | 122.72 |

切换物理存储会改变导出行顺序。首次严格 JSON 比较因此停止。复查表明两个终态的行多重集、值、原始身份、可见性和 anchors 相同，独立语义比较为 4,314 行、2,324 个等价类。正式存储对照使用仓库的存储验证器，对每帧仅排序导出行，完整比较绑定序列与 Run 控制，1,496 个 Run 通过。普通与引用存储终态分别有 3,121 和 2,452 个 live Cell。该指标衡量存活对象数，进程 RSS 还包含计划、索引与分配器。

| 共享节点上的残余策略 | 普通存储 ms / 检查 | 引用存储 ms / 检查 |
|---|---:|---:|
| 原残余查询 | 105.41 / 24,624 | 125.63 / 25,643 |
| 仅列索引交集 | 105.98 / 22,640 | 127.39 / 23,659 |
| 仅 Sieve | **96.72** / 22,229 | 113.53 / 23,246 |
| Sieve + 交集 | 97.13 / **20,602** | **113.09** / **21,619** |

若首要目标是候选检查，优先验证 Sieve + 交集。若要精简第一版，先接入 Sieve；单独增加交集在这份输入上的时间差小且方向不稳定。普通存储的四行是一组，引用存储的四行是另一组。同配置在不同矩阵间存在约 10% 的时间漂移，不能跨表累加收益。两种存储上的「关闭过滤 → 同开 Sieve/交集」各通过 1,497 个阶段快照。

计数包括入口节点维护中的谓词检查、普通或直接种子及 residual/merge 候选。Sieve 自身的操作另计。以引用存储为例，有 39,751 次 Bloom 探测、30,247 次拒绝、13,448 行构建、38,304 行更新及 4,110 行依赖传播。推理时间包含维护。冻结配置的额外深度诊断显示，残余匹配起点从 65,859 降至 35,754，内层行访问从 17,330 降至 13,306。深度 2 从 9,564 降至 8,403，深度 3 从 5,342 降至 3,343。规则分布随分流变化，固定基线规则权重的共同支持质量为 92.55%。逐层直方图、概率、固定权重曲线及两组审计在测量结果中。历史 fact、loopfact、raytrace 上也有 Sieve/交集证据，所用旧版本另见 [SIEVE_JOIN.md](../SIEVE_JOIN.md)。

## 执行流程与复杂度

范围以当前 Cell CPU 为核心，向上跟踪共用编译管线，并区分 Metal 后端。按已跟踪的物理源码行计，`engine/cell-runtime/src` 有 27 个 Rust 文件、14,337 行，`runtime.rs` 2,346 行，`graph.rs` 2,003 行。前者的 Executor 有 38 个字段，后者的 Graph 有 49 个。Python 的 analyzer、IR、compiler 分别约 1,229、814、4,950 行，含各自测试；engine/metal 的 Rust/Python/Metal/Swift 文件合计 4,517 行。分析不把导入的 egglog 内核、生成代码和实验结果算作 CPU 执行器实现。

Rust 执行器源码里出现 40 个不同的 `CELL_CPU_*` 名字，54 个直接读取这些名字的环境变量调用点。部分变量是枚举、诊断或兼容开关。比行数更值得拆分的是 `matches` 约 420 行里交织的入口选择、缓存授权、反证、残余执行、见证收集和绑定去重，以及 `run` 中查询、提交、repair、维护和 checkpoint 所依赖的隐式阶段约束。[查询入口](../../../engine/cell-runtime/src/runtime.rs) · [图及修复](../../../engine/cell-runtime/src/graph.rs)

| 阶段 | 当前数据流 | 主要复杂度与风险 |
|---|---|---|
| 编译与加载 | source → 结构键 → Analyze/Bake → marker 源码 → typed core/Recipe → CPU 计划、merge 和入口调度 | 同一算子的 slot 规范化、消费者投影和计划描述跨多个分析器/运行器存在。把选择逻辑集中在编译器，保留 Rust 对类型、完整覆盖和控制边界的独立验证。Python/Rust 的重复验证有正确性价值。GPU regions 属于另一个物理 lowering。 |
| Run 取数 | 源调度给出规则和水位，旧路径按 reader 扇出到每条规则的 pending set；新入口按表/节点合并变化 | 旧路径开销随「变化见证 × 消费者」增长。新路径随「变化见证 × 涉及节点」维护，按消费者水位对有序 epoch 索引做范围查询，另付实际交付数量。冷节点扫描当前表，含固定等价身份的节点遇 union 可要求全刷新。 |
| 求完整绑定 | 入口包 + 私有后缀，优先使用合法的固定键程序、可证覆盖和残余匹配，最终按完整输入去重 | 固定键查找还承担 canonicalization 和虚拟行解码。不完整键选索引桶或交集，多值后缀的最坏成本仍随各层扇出的乘积增长。命中一个入口不能证明整个后缀。 |
| 密封与执行 | 全部 LHS 在一个快照读完，生成 StagePatch，再按源顺序执行原 RHS、构造、set 和 union 请求 | 工作量随绑定数、每个 RHS 操作数及自定义 merge 成本增长。构造复用仍需确认实际结果。顺序敏感 merge、物理身份分配、hide/delete 和错误顺序影响可观察结果。 |
| 修复与发布 | 递归完成 pending unions、受影响的键归并与同余，处理存储迁移，再更新查询索引、共享节点、receipt、各观察器与 GC | 成本由受影响的 use/父行、碰撞桶和级联轮数决定。仅计算 union/find 次数会遗漏大部分 repair。相同 eclass 结果和相同构造键对应不同的转发权限。 |
| 恢复与验证 | 权威图、调度栈、水位及必须保存的局部完成状态进 checkpoint，部分缓存冷重建 | 删除缓存前需区分可重算的数据和防止重复非幂等效果的状态。后者需要版本、阶段和依赖证明。 |

加载端也有一个具体的瘦身点。`Plan::parse` 会重建 expected JSON 和执行计划以验证消费者投影，`Scheduler::new` 随后克隆计划并为节点建立状态。可以共享不可变的已验证计划，在禁用或首次消费前延迟动态状态分配，单列加载时间与峰值 RSS。

可定位的重复维护有三处。Scheduler 持有按节点的 pending、当前 packets、epochs 和行缓存；Spine 仍持有旧入口缓存、发布队列、来源与上下文端口；retained/prefix 又持有 read-domain 订阅、相关分支树和消费者水位。底层还分别分发 `events`、`query_changes`、same-key 转发和索引变化。三者对「当前行」可以共享物理服务，对「一个绑定已完成」的权限却不同。当前 `matches` 可以先尝试部分 Spine，再转到完整 retained provider；这类组合会付出两套路由成本。Sieve 会屏蔽部分反证路径，merge 程序命中后走另一条剩余查询路径。许多开关因此既有顺序依赖，也有前置条件。[节点状态](../../../engine/cell-runtime/src/entry_schedule.rs) · [接续状态](../../../engine/cell-runtime/src/stage_spine.rs) · [保留域](../../../engine/cell-runtime/src/retained.rs)

## 合并后仍值得优化的工作

- **残余后缀**。入口共享解决了重复种子验证，节点单独开启时仍有 17,330 次内层访问。先把完整多值端口域、相关参数顺序与失效条件写入受验证的计划，再决定哪些域值得长期保留。Sieve 的成功说明在部分后缀先做廉价必要条件也有价值。
- **空工作与屏障**。1,496 个 Run 里有 917 个空 patch。给 Run 预编译有效 reader/dirty 集，测空 Run 与脏但失败的查询各自消耗。零绑定和零变更必须分别记账，有限重复、naive replay 和 probe 仍由源控制树决定。
- **RHS 与身份**。19,188 次构造请求中有 15,953 次复用。如果源 SSA、删除 epoch 和修复后的键足以证明已知结果，可在规则级消除查找。其余等价键可能由本 Run 前序 RHS 刚产生，必须读提交时的状态。对 2,168 次 merge 分别按有序/格/结构键契约统计。
- **配置与归因负担**。节点调度与 Sieve 的组合已能单独成立。优先测真实尾部工作、短命分配、列索引首次构建与负证据失效，保留 maintenance 和 RSS。当前局部性证据是参数共享和重复访问减少，CPU cache miss、内存带宽和跨核 cache-line 流量仍需硬件采样。

## eggcc 的真实三 pass 扩展性

Apple M3 Max，有 12 个性能核、4 个能效核，48 GiB 内存，macOS 27.0.1。使用 `check_statewalk@ae80f82` 的原始 sum-bits.bril，生产 Tiger 按原链将前一 pass 的提取结果交给下一 pass。原驱动在 `new_single_threaded_egraph` 里请求 `num_threads(1)`，并会忽略全局池已初始化错误。`--eggcc-schedule parallel` 选择规则调度。实验在隔离源码中使池宽可控，并断言实际 Rayon 池宽为所请求的数字。三种宽度的初始化均成功。

构建了两个 release 驱动。一个沿用已有外层调度 profiler，另一个只开放池宽。每个驱动运行六个区组，覆盖 1/4/16 的全部排列，合计 36 个新进程。每个线程数六次，中位数如下。1× 为相应口径的单线程时间除以本行时间。

| Rayon 线程 | 三 pass 调度 ms | P1 / P2 / P3 调度 ms | search+apply / insert-merge / rebuild 合计 ms | 仅改池宽的 CLI wall ms | 调度倍率 / CLI 倍率 |
|---:|---:|---|---|---:|---|
| 1 | **81.77** | 25.13 / 12.50 / 44.17 | 29.47 / 3.16 / 14.48 | **274.94** | 1.000 / 1.000 |
| 4 | 89.48 | 28.57 / 13.44 / 47.40 | 36.85 / 3.50 / 14.69 | 284.24 | 0.914 / 0.967 |
| 16 | 109.45 | 35.04 / 16.14 / 58.42 | 54.31 / 4.27 / 15.97 | 312.54 | 0.747 / 0.880 |

池宽驱动内部编译时间也从 244.99 增至 255.25、282.53 ms。调度 profiler 中 execution（含准备）分别 204.03、213.14、237.81 ms，提取 wall 分别 37.02、35.97、38.74 ms。各指标先按每次调用合计再取中位数。CLI 六次包含一个明显的单线程首次进程离群值，原始样本全部保留。

三种宽度的每个 pass 输入 SHA-256 相同，两个驱动的最终优化程序均逐字节相同。三 pass 节点/类计数为 2259/1658、1719/1266、3263/2251。1 线程的逻辑匹配数为 3797、2263、6506；4 和 16 线程为 3798、2260、6497。这里验证了产物与下一 pass 输入，可观察到的逻辑匹配序列可能随执行策略变化。各 pass 原生完整图的同构比较未测。

本机没有复现「4 线程 1.3×，16 线程约 1×」这两个具体数值，却复现了很差的扩展性，且 16 线程实际更慢。去掉调度探针后，进程及已等待子进程的 CPU 秒 / wall 秒约为 0.98、0.99、1.04。这个整段平均值不能定位某一个锁，但说明 16 个 worker 在 CLI 的大部分 wall 时间没有形成 16 核有效工作。回退集中在 search+apply。锁定的 egglog 内核 `ebba7bb` 对数据库级并行、建索引、表操作设有粒度门槛，规则并行会分派 plan、克隆执行状态和合并报告；bridge 的 rebuild 也有串并分支。当前剖面没有按门槛、等待或 cache miss 分别归因。异构核心和系统调度同样限制跨机器外推。

## Cell 的局部性可以换来多少并行度

已经测到的局部性收益是同一变化的入口复用、参数复制减少和较少的候选检查。多个消费者依然共用行缓存、canonical parents、函数值、动态索引与发布状态。这些变化降低了单线程工作量，同时缩小每个任务的计算量。硬件 cache miss 和内存带宽尚无本轮实测。下面分开量化只读阶段的工作量、真正的线程池回放和依赖风险。

### 真实 Run 的工作分布与模型

用隔离的诊断构建记录每个原始 Run 的每条规则匹配耗时和绑定数，核对终态及每步控制，再用同 lane 第一轮无插桩的 search wall 按相对权重归一。除搜索外的时间固定串行；单一 Run 内允许自由分配只读工作，Run 之间保持屏障。整段上限为 `T / (T − S + S/p)`。完整规则不可再分时，每个 Run 的下界为 `max(总工作/p, 最大单条规则)`，另将规则由重到轻发给当前最闲 worker 得到 LPT 估计。共享缓存冷启动、跨核流量、冻结、归并、调度和负载预测误差均未收费，这是工作模型。

| 配置 | 对应干净推理 / 搜索 ms | 4 核任意切分 / 按规则 LPT | 16 核任意切分 / 按规则 LPT |
|---|---|---|---|
| 复制 marker，节点单独开 | 114.08 / 61.14 | 1.67× / 1.55× | 2.01× / 1.66× |
| 同存储，节点 + 跨阶段 Spine | 141.63 / 66.56 | 1.54× / 1.46× | 1.79× / 1.54× |
| 普通存储，节点 + Sieve/交集 | 98.12 / 46.85 | 1.56× / **1.45×** | 1.81× / **1.53×** |

第三行有 1,496 个 Run，917 个没有提交绑定，1,050 个没有图变化。搜索阶段中位数 **2.21 µs**，P90 为 63.69 µs，P99 为 462.74 µs，最长 2.60 ms。1,017 个 Run 的整个搜索短于 10 µs。58,020 次规则调用中约 91.4% 在诊断里短于 1 µs，含干净/空表短路。最重约一成 Run 占 77.2% 的搜索时间。若目标是比单线程快 1.3×，第三行 4 worker 的零开销按规则模型给出的总开销余量仅约 **8.0 ms**，要同时容纳冻结、唤醒、负载偏差及结果归并。只增加线程数时，16 对 4 的整程序模型收益很窄。需要对重尾 Run 做粗粒度分块，且保持已经节省的串行工作。

### 在真实输入上运行线程池

从节点单独开启的原始时间线捕获真正进入参数投影的 7,613 份工作。其余 700 次检查复用同参数、不同 epoch 的包。保留 573 个非空 Run 边界，每批中位数 4 项，最大 285 项。输入包含真实行值、别名约束和已经 canonicalize 的字面量，逐项对照实际执行所产生的接受/拒绝和全部投影值。复用已启动的 Rayon 池，每进程预热两次，计十次，两组逆序排列。下表为完成整段投影的毫秒中位数。

| 提交方式 | 直接串行 | 1 worker | 4 workers | 16 workers |
|---|---:|---:|---:|---:|
| 协调线程按非空 Run 进入池 | **0.232** | 2.945 | 4.073 | 32.232 |
| 协调循环驻留池内 | — | — | 0.843 | 13.053 |
| 驻留池，少于 64 项直接串行 | — | — | 0.466 | 2.761 |

这是实际多线程执行的纯投影片段回放。解码、冻结输入、线程池创建、结果核对和发布均在计时外，完整 Cell 引擎的多线程端到端速度仍待实现。即使小批回退，入口这层的工作也太轻。此结果直接反对把每个入口节点、每个参数包或每条 notification 都提交为并发任务。

### 可并发边界与准备工作

| 区段 | 可行方案 | 当前障碍与处理顺序 |
|---|---|---|
| 不同编译单元/独立 egraph | 独立进程或独立 executor 并发，适合批处理吞吐 | 内存、工具链和产物路径隔离；单个 sum-bits 的延迟需另测。这是风险最低的吞吐路径。 |
| 静态分析与计划生成 | 分规则生成候选、足迹、类型化 projection，稳定排序后统一编号 | Canonical node ID、manifest 指纹及 solver 的全局选择需确定；这段不在推理时钟内。 |
| 入口更新/解码 | 先按实际 demand 汇总本 Run 需要的节点和 witness，在单一所有者上刷新并冻结，批量借出只读参数 | 当前 `seeds(&mut self)` 会惰性刷新，两个 worker 可争用同一行缓存、epoch 索引与 pending。优先消除逐规则复制 route 列表、预留工作区；纯投影保留小批串行。 |
| 精确残余匹配与纯 guard | **第一项在线并行候选**。冻结规范代表元和查询索引，按重规则或同一 pivot 的互斥 witness 区间静态分块，worker 产生私有 binding/witness 缓冲 | 当前 `matches(&mut self)` 同时消耗 dirty/pending、刷新索引、更新 receipt 来源与统计。改成 prepare → read-only match → collect；同一 self-join 的 atom/见证身份和 delta 所有权必须保留。 |
| 绑定合并、RHS 准备 | 按规则序号与原有完整输入序归并线程局部结果，固定 tie-break、去重及 source ordinal 后密封 StagePatch；纯 SSA 计算可随已隔离的参数并行 | 相同结果可能有多个 cursor/witness。任取最先完成的 worker 会改变物理来源。副作用和遇错时的可观察前缀需要按源顺序提交。 |
| 构造、set、merge、union | 首版保留单一提交者。后续按已证明的不相交键分组，先分配确定的身份，再提交实际结果 | hashcons 同键竞争、全局 Cell 身份、ordered merge、hide/delete、union 后两键碰撞和新启用的规则都会跨分片。即使最终值可交换，也需保留中间构造、epoch 与可见性。 |
| repair、发布、GC | 先收集和排序独立的脏键/索引增量，单线程合并到固定点。稳定表分片上的只读扫描可作为第二阶段候选 | parents、反向 uses、函数端口迁移、同余、storage forwarding、引用计数形成反馈。所有 worker 归还当前 epoch 借用后再回收。固定 Run 边界先于跨 Run 流水化。 |

实际非空绑定分布也限制并行提交。仅 275 个 Run 有多个产出绑定的规则。同一 Run 内共 14,576 对不同活跃规则，3,603 对有共同声明写表，4,919 对至少一侧可 union。把读写交叉、写写交叉和任何 union 都作为保守危险标记，共标中 8,790 对。这是表级足迹筛查，包含已经密封的 LHS 读取；它既高估实际键冲突，也遗漏单条规则内部绑定之间的冲突。不能以剩余配对数量直接推导并行提交权限。

这些 Rust 所有权边界需要先落地。编译计划和 epoch 快照只读，worker 借用切片或 arena 句柄；共享结构键已有不可变 Arc DAG。Graph 的 `Cell<u64>` 查询计数迁到 worker 本地计数器；`Rc<RefCell<Context>>` 的写入、来源登记、动态索引首次构建和动态去重归单一阶段所有者。仅在需要跨线程时提升共享对象的生命周期。一行一个原子引用计数、一表一把热锁都要单独计入性能账。[共享入口](../../../engine/cell-runtime/src/entry_schedule.rs) · [有序 Run 与 StagePatch](../../../engine/cell-runtime/src/runtime.rs) · [同键修复与存储](../../../engine/cell-runtime/src/graph.rs)

## 下一次实现的验收门槛

1. 先完成配置归一和单一入口提供者，将普通存储 + 节点设为研发基线。保留串行 reference 与旧产物加载，以独立配对决定 Sieve 的选取条件。在第二个非训练负载及高 union/高 fanout 负载通过前，暂缓更改全局默认。
2. 提取不可变 `RunSnapshot`、单线程 `ChangeBatch` 和 worker 私有 `QueryScratch`。第一版仍在一个线程调用同一接口，必须通过完整状态、绑定序、visibility、merge 值、有限 Run、饱和、checkpoint/replay。单线程本身如有回退，先定位分配、复制和锁引入的位置。
3. 对重 Run 启用常驻 2/4 worker，先处理残余查询。按预估节省时间超过唤醒、打包和归并成本来选并行阈值；轻 Run 直接串行。记录每 Run 的实际忙碌时间、等待、最大任务占比、跨 worker 数据量和归并耗时。先在 P 核范围测试，再独立记录 16 核混合配置。
4. 上线判据采用同二进制强制串行 / 2 / 4 / 8 / 16 线程，交错顺序、相同输入及配置、完整状态与绑定序、RSS、候选和端到端时间。特意覆盖非幂等函数、同键并发提案、union 后函数碰撞、隐藏再插入、慢消费者。建议先要求 4 线程在两个重负载均有可复现净收益，小输入能回到串行成本附近，再讨论分片提交。

本轮通过完整 Cell 对照和隔离投影 oracle。当前 Cell 与原始 native 的历史全 Pass 3 差异、既有事件计数测试 `16 < 16` 均沿用此前记录。本轮没有将配置升为生产默认。原始样本、时间分母、阶段曲线、开关到源码映射与复现入口见 [测量数据](results.json) 和 [复现说明](REPRODUCE.md)。
