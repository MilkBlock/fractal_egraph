# 手改生成的 .egg：marker 已保证的结构漏了多少

先手改，再测量；本轮没有修改编译器或求解器。`run.py` 只是把下列指定
规则的编辑重放到冻结的生成文件，不负责自动发现可优化的规则。

结果：**确实有遗漏，长链中更大的遗漏是重复存了一份规范输入。** If 中
找到的直接冗余很少，删除后没有解决它的主要 Join 瓶颈。

## 1. 已有 marker 保证的 LHS 检查

长链原退休规则大致为：

```text
大 marker(新根, 旧链根)
六个 Cano-Plus 读取 + 一个 Cano-Extend 读取
小 marker(旧链根)
    → subsume 小 marker
```

其中旧链根已经由大 marker 携带，六个输入变量和 next 均不用于动作。
可以改为：

```text
大 marker(新根, 旧链根) + 小 marker(旧链根)
    → subsume 小 marker
```

保留小 marker 的 LHS 原子，因此它后来出现时仍能触发退休。没有通过
删除消费者或放弃通知来降低工作量。

另外手改了三项 AC 的两个退休规则，以及 If 的 `retire_2`。后者的
Summary-2 已直接携带 `Single(p0)` 的值，重复读取该节点不会得到新 binding。
其他仍须读取节点才能取得 binding 的地方保留。

| 输入 | 生成规则中的读取项 | 手改后 | 本次确认可省 |
|---|---:|---:|---:|
| 长链嫁接 | 19 | 12 | 7 |
| 三项 AC | 25 | 22 | 3 |
| If 小子集 | 711 | 710 | 1 |

这些是选定样例的显式冗余，不是整个仓库的完整冗余普查。

## 2. RHS 重复取得已有结果

对 If 的两个实际执行过的继承规则，手动复用了 owner marker 中的 `r3/r4`：
它们已经是 `Get(Single(p),0)` 的结果。保留先前建立 Single 别名的 union，
后续直接传递这个结果字段，去掉重新取得 Get 结果以及对应的自 union。

两个规则合计减少四个不同 Get 调用项、四条 union。结构更新分数从
1978 降到 1970；但它们合计只触发 100 次，主要失败搜索仍在，运行时间
没有明显改善。没有把外部条件当作已知事实删除。

## 3. 用目标 marker 替代一个物理节点

长链的目标 marker 原来只有 `(新根, 旧链根)`。手工增加 `next` 字段后：

```text
小 marker(旧链根) + Extend(旧链根, next)=新根
    → 大 marker(新根, 旧链根, next)
      subsume 小 marker
```

这里省掉 `Cano-Extend` 的构造及 raw/canonical union。后继转移只需要
marker 的字段；导出时也直接读取 next。退休规则已经不再解码 Extend。
因此省掉节点的同时没有留下仍依赖它的读者。

每个大 marker 多存一列，每个实例少存一个 canonical 节点。本例的目标
根值已由外部 Extend 提供；这不是“任意新 RHS 都不用生成”的结论。

## 4. 原始输入已经是选中的 spine，直接借用

这个长链样例的输入本来就是选中的七输入右链。生成程序却又复制出六个
`Cano-Plus`，并把它们与原始 `Spine-Plus` union。

进一步手改：发布小 marker 时直接使用已匹配的输入链；省掉这六个复制
节点和对应 union。显式导出改从 marker 指向的原始输入链读取参数。
结合上一步，运行时完全不需要 `Cano-Plus` / `Cano-Extend`。

这是“借用已经规范化的输入”的特例。输入形状不等于所选 spine 时，不能
照搬。原始输入节点没有删除；省掉的是同一实例内的 raw/Cano 重复存储。

直接对比可执行单样例文件：`long-before.egg` 与 `long-after.egg`。两者均
包含显式导出和原例的 `Done` 检查。它们不是完整的七项 Add/AC 优化器。

## 单次原生 bench

沿用同批冻结 Bake、同一组 1000 个输入，不重新分析或求解。每项计时
一次，没有取平均或选最快结果。native 为同一当前内核普通执行，非 pristine。

| 输入/变体 | 推理 ms | 候选行访问 | canonical 节点 | 全部表行 | 峰值 RSS MiB |
|---|---:|---:|---:|---:|---:|
| 长链：原生成程序 | 15.111 | 96,000 | 7,000 | 25,000 | 38.19 |
| 长链：只删重复 LHS | 11.078 | 53,000 | 7,000 | 25,000 | 37.23 |
| 长链：再省目标节点 | 10.255 | 53,000 | 6,000 | 24,000 | 35.83 |
| 长链：再借用输入 spine | **5.215** | 53,000 | **0** | **18,000** | 37.05 |
| AC：原生成程序 | 19.748 | 36,000 | 3,000 | 12,000 | 31.03 |
| AC：删重复 LHS | 6.535 | 33,000 | 3,000 | 12,000 | 30.31 |
| If：原生成程序 | 99.061 | 1,276,552 | 3,201 | 33,313 | 301.11 |
| If：删重复 LHS | 100.924 | 1,276,552 | 3,201 | 33,313 | 297.08 |
| If：再复用 RHS 结果 | 101.393 | 1,276,552 | 3,201 | 33,313 | 305.81 |

当前内核普通执行的推理时间分别是：长链 8.602 ms、AC 6.077 ms、If
44.904 ms。长链最紧凑变体的总执行时间为 134.01 ms，普通执行为
138.15 ms；解析/插入输入占大头。这里的推理收益不等于同倍率端到端收益。
完整导出的时间另见 `results.csv`。

AC 单次计时的变化远大于候选行下降幅度，不能据此宣称稳定三倍加速。
RSS 也没有随行数等比例下降；更宽的 marker、索引和分配器均计入进程峰值。
没有把表行减少当作字节压缩率。

按本次要求，只比较恢复后的节点/类数量，不逐事实检查图等价：

- 长链全部变体：18,000 节点、18,000 类。
- AC 两个变体：15,000 节点、7,000 类。
- If 三个变体：16,208 节点、14,108 类。

数量匹配记录为规模对照。计数在独立进程完成，没有导出完整节点 JSON；
计时进程不做计数扫描。原始的 source `Done` 检查也通过了，但不替代全图证明。

## 对求解器缺口的判断

小规模手改已经确认至少 11 个冗余 LHS 读取。对长链，一个零 match 的退休
规则就浪费了大量搜索；对 If，直接重复检查不是主要成本。

更值得加入求解空间的是**物理表示的选择**：

1. marker 中直接携带 binding，省掉仅供解码的节点；
2. 输入已经满足 canonical spine 时，借用原节点；
3. 所有消费者与导出都根据该表示读取，不能只删除 RHS 构造。

这次的手工方案还没有注入 Gurobi。相关 `.diff`、编辑理由与完整生成库
均由脚本保存；没有增加新的 fragment 辅助表，也没有删除规则来避开搜索。

## 复现

```sh
out/cell-spine-venv/bin/python experiments/cell_spine/manual_marker/run.py \
  --ablation-root out/spine-joint-ablation --output out/manual-marker-new

# 看手改后的单样例 .egg
target/release/examples/native_math_baseline \
  experiments/cell_spine/manual_marker/long-after.egg
```

编译器输出目录缺失时，先按 `../joint_runtime/README.md` 生成冻结输入。
bench manifest 新增 `counts: true`，可在不传 graph 路径时仅获得节点规模。
脚本默认重建 runner；已有相应二进制可使用 `--skip-build`。
