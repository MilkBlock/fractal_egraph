# 连续 rewrite 的在线组合实验

已实现“预处理候选＋运行时局部观察＋安装等价快捷规则”。执行对象是仓库内真实 egglog；没有改用 SharedStore，也尚未将此机制接入 slotted-egraphs。

**本轮结论：组合的正确性成立，链式负载的推理轮次减少，但没有测到整体加速或内存下降。不能把轮次下降当作性能收益。**

## 组合具体做什么

例如两条源规则：

```text
r1: Mul(x, Add(y,z)) → Add(Mul(x,y), Mul(x,z))
r2: Mul(a, One)      → a
```

将 r1 的 RHS 左子项和 r2 的 LHS 合一，得到输入限制 `y=One`：

```text
快捷规则：Mul(x, Add(One,z)) → Add(x, Mul(x,z))

两步依据：
Mul(x, Add(One,z))
  → Add(Mul(x,One), Mul(x,z))
  → Add(x, Mul(x,z))
```

组合器使用 egglog 的表达式解析器，先将两条规则的变量重命名为不同命名空间，再进行带 occurs check 的一阶合一。它保存源规则编号、重叠位置和中间表达式，不通过字符串拼接猜测变量关系。

当前支持根部及 RHS 内部的构造器位置，排除纯变量位置。仅支持单一 E sort 上的无条件构造器 rewrite；不支持条件规则、任意 action、subsumption、带副作用的 primitive 或跨类型组合。每个候选两侧最多 32 个 AST 节点，候选总数上限 64。

## 运行时如何“边走边看”

```text
预处理原始规则的两步组合候选

每一批输入：
    插入真实 egraph
    重复直到饱和：
        执行原始规则和已启用的快捷规则
        从 Survived 源规则匹配中读取绑定
        在当前 canonical 图中定位第一条规则的 RHS 子区域
        检查该区域是否还能匹配第二条规则
        两次观察后，将对应快捷规则列为待启用候选
        每轮结束安装候选，最多启用 8 条
```

观察到的是“R1 匹配＋其 RHS 区域当前可匹配 R2”，不是“R1 此次提交了该节点并导致 R2 执行”。候选的等价性来自规则组合本身，历史仅决定优先启用哪些候选。

原规则始终保留，快捷规则可以在未来任何满足其 LHS 的区域使用。因此该模式不主动消除中间节点；它改变调度和到达结果的路径，不改变所测最终闭包。

当前发现器每轮读取构造器行建立局部索引，不是内核共享匹配计划。它对 `(candidate, target e-class)` 去重，最多处理 4,096 个 Survived 事件、128 个不同局部探测；每次探测最多访问 256 次并保留 16 个绑定分支。达到候选总数或 8 条选择预算后关闭发现和 trace。漏选候选不会影响原规则的可用性。

## 四组对照

|模式|行为|
|---|---|
|original|只执行原规则，无组合预处理和 trace|
|observe|相同的有界发现、虚拟选择和停止策略，但不安装快捷规则|
|static|运行前安装全部预处理候选|
|dynamic|运行时观察后才安装，最多 8 条|

观测计数仅来自实际开启 trace 的阶段，不是各模式可直接比较的总匹配次数。

## 测量结果

3 次独立进程的中位数；每批 256 个不同输入，共 4 批，每批运行至饱和。

|数据|模式|总轮次|安装快捷规则|推理阶段|总耗时|
|---|---|---:|---:|---:|---:|
|八步链式正对照|original|36|0|1.54 ms|18.06 ms|
|同上|static|20|7|2.38 ms|19.34 ms|
|同上|dynamic|24|7|5.49 ms|22.09 ms|
|算术化简|original|12|0|5.09 ms|44.44 ms|
|同上|static|12|6|15.18 ms|56.88 ms|
|同上|dynamic|12|3|28.07 ms|67.92 ms|

算术数据为 `Mul(Neg(Neg(Var i)), Add(One,Zero))`，使用分配、乘一/乘零、加零和双重取负规则。链式数据是人为设置的 `S0(x) → … → S8(x)`，只用于验证较长路径能否被快捷规则缩短。另有不触发这些规则的 `Add(Var i, Var j)` 负对照，动态模式没有安装快捷规则。

动态模式保留分配量也增加：链式约 2,518 → 2,695 KiB，算术约 3,570 → 5,134 KiB。额外候选、编译规则和索引都需要内存。

推理计时包含 trace、局部发现及动态安装；总耗时还包含源规则准备、候选预处理、引擎初始化和输入解析/插入。静态安装在推理循环外，但包含在总耗时中。内存包括实际引擎、外部 roots、候选目录及选择记录。峰值 RSS 还包含之后的完整闭包验证。

## 正确性与复现

6 项测试覆盖 occurs check、重复变量约束、根部及嵌套组合、每个候选的实际两步执行，以及三种负载在四种模式下的完整饱和图一致性。

72 次测量运行在不同分配 ID 下，用最小 ground representative 给 class 命名，然后比较全部构造器记录及 roots；完成 66 次跨运行闭包比较。不是只检查最终答案或 hash 是否一样。若某一波 32 轮内未饱和，程序直接失败。

```sh
cargo test --bin rule_combine
cargo build --release --bin rule_combine
python3 experiments/rule_combine/run.py

# 单独查看在线选择及候选推导
target/release/rule_combine dynamic algebra 64 4
```

`results/rule_combine/candidates.json` 保存全部预处理候选及中间推导，`runs.json` 保存每次运行和启用时机，`summary.json` 与 `report.md` 保存汇总。

下一步应优先评估候选的匹配代价和实际路径收益，再考虑安装；在没有收益模型前继续扩大组合长度，很可能只是增加更多匹配工作。这里没有证明相对于 slotted 基线的额外收益。
