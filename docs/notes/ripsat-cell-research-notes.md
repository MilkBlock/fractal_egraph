# RipSatCell：从执行历史到可复用的推理

## 1. 我们真正想复用的是 binding

一条 rule 在哪里执行，取决于它的 LHS binding。只记下 `R1 → R2` 没有什么用，还得知道 R2 在 R1 的哪个结果上执行，以及它从外面拿了什么。

所以 rule composition 应该记录：

```text
前驱组合 + rule + relative binding + 外部输入 → 新组合
```

relative binding 是变量、位置和别名的对应关系，不是简单的 `binding + 偏移`。这部分有规律，组合才有机会复用。

## 2. Coarse 和 smooth 取决于当前上下文

当前组合已经提供了执行所需的信息，这次 apply 就是 smooth；还需要外面的 fact、等价关系或条件，就是 coarse。同一条 rule 在不同位置可以属于不同类型。

历史可能有分叉，也可能由多个 producer 汇合，不必硬压成链。截取一段历史时，缺掉的依赖要变成显式输入。

之前的 prefix 分块是为了限制历史爆炸，现在不再把它当成语义基础。babble 也暂时不放在主线上。

## 3. Ripen 把一段局部推理算完

把 coarse composition 的输入放进局部 egraph，用 RipenInput 表示边界参数，再按对应的规则和 schedule 推进，这个操作叫 ripen。

得到的局部封装叫 RipSatCell。它有内部结构、输入接口和对外提供的事实。RipenInput 是有类型的参数，不是随便匹配任何东西的通配符；两个槽位在实际使用时也可能绑定到同一个 e-class。

局部算完，不代表以后永远不用算。新的边界事实或 union 仍然可能启用新匹配。

## 4. 不同阶段必须有不同的 Cell 契约

从 history 提取 Cell 的价值之一，就是知道这些操作发生在什么阶段、按什么顺序发生。

eggcc 的 substitution 会先生成 `DelayedSubstUnion`，下一阶段才真正 union。如果 bake 时提前合并，就可能让替换看到自己的结果，继续无穷展开。

因此，提取、ripen、判等和执行都要保留阶段信息。不能只因为最终节点长得一样，就把两个阶段的转移当成同一个。

## 5. CSCS 和 CCSS 是两种接法

CSCS：前一个 Cell 的结果参与下一次 coarse apply，再推进出后一个 Cell。

CCSS：先把两组 coarse 输入拼起来，再一起推理。

共享节点能帮助确定 binding，但“有一个交点”不等于值得合并，更不等于两个执行顺序可以互换。优先沿真实 consumer 的依赖组合，不枚举所有 Cell 配对。

CoarseLayer / SmoothLayer 可以继续用来描述历史，但不必强迫所有结构排成一条 CS 链。

## 6. Cell 可以从 root、input 或内部接口接上去

例如 A 的 root 是 `Add(x,y)`，外面出现 `Add(A.root,z)`，新的 coarse rule 就可以从 root 一侧 graft。

一个 LHS 也可以同时用到几个 Cell 提供的事实。关键是保存接口之间的 binding，不是限制它只能从某一个方向接续。

## 7. Cell egraph 归一化的是状态，不是完整历史

不同 rule apply 轨迹可能得到相同的局部闭包，它们应该落入同一个 Cell e-class。轨迹保留为构造路径，不能永远塞进状态身份，否则 `Swap(Swap(Swap(...)))` 本身就会无限长下去。

还要分清三件事：

- A 生成了 B：历史上的构造关系。
- B 里面包含 A：存在对应的结构和 binding。
- A 与 B 等价：在相同接口、阶段和规则环境下可以互换。

egraph 的 union 表示第三种，不会自动找出第二种。

## 8. 大 Cell 应该尽量由小 Cell 表示

我们猜测，大闭包的增长主要来自少量重复的边界组合。因此可以尝试存成：

```text
小 Cell 的引用 + binding + 边界连接 + 新增的 residual
```

residual 是已有组成部分还没解释的事实和等价变化。比较前必须对齐身份和接口，不能直接拿两张图的本地 ID 做减法。

真正的收益要看：这些引用和参数是否比展开结构便宜，以及找到合法连接是否比原来的 Join 便宜。小 Cell 经常出现，还不足以回答这两个问题。

## 9. Union 是状态维护的难点

`x = y` 会让 `f(x)` 和 `f(y)` 等价，也可能让两条旧事实突然能连接。hashcons 在 canonical 子项相同时去重，rebuild 负责传播这种变化。

不同输入槽位发生 union 后，可能出现原先没有的内部推理。不能只更新代表元，就认为 Cell 已经到了新状态。

我们需要区分：已知闭包、后来新增的 effect、哪些变化已经由已知转移解释。哈希可以帮忙找相似状态，不能代替等价证明。

## 10. Bake 学的是可复用转移

先跑代表性样例，从 history 提取 Cell、relative binding 和阶段内转移，形成库。然后冻结库，在新样例上测试。

当前有两个不同的东西：观察到的结构模式，以及已经能合法执行的闭包转移。前者不能直接冒充后者。

之前的“44 个 Cell”实际是旧实验的 44 个快照，去掉背景项后用了 43 个模式。约 20% 的那项数字是有效 apply 签名命中率，不是通用结构压缩率。

## 11. 用 fragment 选择 abstraction 的轨迹

运行时让 abstraction 表示一个 Cell 状态，并主动发布白名单 fragment。fragment 带上 owner 和参与边界计算的参数。

```text
Cell A 发布的 fragment
+ Cell B 发布的 fragment
+ binding 条件
    → 执行已知转移
    → 生成 Cell C，发布新的 fragments
```

fragment 应该由状态或转移直接给出，不能为了生成它再做一次同样昂贵的 Join。连接变量也不能省掉，否则会把原本不相关的两组 binding 错配起来。

不同 Cell 可以发布同一种 fragment sort，供多个 rule 共享。

## 12. 白名单主动缩小探索空间

我们不再要求执行原始 eggcc 的全部匹配，而是保证执行 bake 库里满足条件的转移。每条转移仍须正确，但库外的优化机会可以暂时不探索。

这可以先在 rule level 实现：生成 fragment 规则，控制 ruleset schedule，不同时保留无条件的全局 fallback。egglog 的 semi-naive 仍可服务这套更小的规则程序。

类型、上下文和延迟 union 等阶段义务不能顺手删掉。实验应比较：原版、相同白名单的普通执行、白名单加 Cell 转移。这样才能区分“少搜索了”与“同样的探索做得更快”。

## 13. FractalComb 编码重复的推理规律

FractalComb 不只是相同 rule 重复出现，而是 binding 和 effect 按同一种方式变化。它可以是线性接续、交替组合，也可以一层产生多个后继。

启动前可能需要先积累一些 effect；满足启动条件的状态叫 trigger state。后续可以写成：

```text
state[k+1] = T(state[k], input[k])
```

A、B 两种 FractalComb 一般不交换，也不“正交”。实际历史可以交错，不一定先把 A 跑到底再跑 B。

## 14. 幂等、重入和无限增长是不同的事

交换两次，项可能回到原样，但第一次已经加入的节点不会消失。在固定上下文中，后续交换可能不再产生新 effect，这时是幂等，不是无限生成。

新的 binding 或 effect 下再次出现触发结构，叫 non-trivial reentry。它是发现 FractalComb 的线索，不证明会无限增长，也不证明会停止。

ripen 超时或超过空间限制，只说明没算完。不能把 unfinished 直接叫 infi。

## 15. 耗散的是展开条件，不一定是节点

`1+1+1+1+1 → 2+1+1+1 → … → 5` 中，耗尽的是剩余位置。图里可能一直只有一个共享的 `Num(1)`，没有把这个节点“吃掉”。

我们区分：能自维持的展开、不断需要外部节点的展开，以及受 length、guard 等条件限制的展开。

擦除衰减参数有助于发现共同形状，但执行时要恢复这些条件。只有证明能持续产生新效果，才称为无限生成的 FractalComb。

## 16. Reduce 可以压缩终点计算，但不能随便删中间 effect

例如在合适的算术条件下：

```text
f(a) → f(a−1)+m
n 次后：f(a) → f(a−n)+n·m
```

终点表达式可以归约，但中间节点可能被其他规则使用。减少执行步骤和省略中间事实，是两个不同的优化。

有限序列上的重复组合可以进一步抽象为 fold / sum。数组、blocking 和并行 scan 需要明确索引、顺序及运算性质，不是出现递归就自动成立。

## 17. Weak dominance 只表示触发包含

如果 A 的局部状态中能找到 B 的输入结构和 binding，就说 A weak-dominates B。这不意味着 A 已经包含 B 的全部闭包，更不意味着 A 比 B 更值得存储。

包含关系、语义等价和成本排序分开处理。多个 apply 点也不自动优于少量 apply 点。

槽位对称性可以进一步减少重复状态，但交换必须保持类型、条件和接口。slotted egraph 是一种工具，不是唯一解法；多 root 可以作为多端口处理。

## 18. 不要再把覆盖率当成压缩率

模式数量乘以模式大小会算重，覆盖率应对实际节点或 fact 去重；e-class 覆盖另算。

内存要算库、实例 binding、索引和缓存。时间要算失败搜索、成功匹配、动作、union/rebuild 和维护。

相同 e-node 规模不代表相同推理质量。最终要比较相同时间的 extraction 质量，或达到相同质量所需的时间。

## 19. 半朴素执行没有承诺“所有工作都便宜”

semi-naive 按每条 rule 的进度处理增量，不是一个跑完就为所有 ruleset 清空的队列。它减少重复搜索，但不保证不会重复推导已有事实，也不保证 union 后的新增连接很少。

规则少了，节点数、等价类数和耗时也不一定一起下降。当前要改变的是探索范围与执行粒度，而不是把 semi-naive 简单称为错误机制。

## 20. 远期目标：把推理轨迹编译成程序

如果大量内部 binding 都能直接传递，一次 Cell 转移就可能替代多次“匹配—生成—再匹配”。FractalComb 再把重复转移变成循环或归约。

GPU 是否合适，取决于它最终能否形成成批、紧凑的计算，而不是把 slot 写成矩阵就自动加速。

FlashAttention 是更远的目标：需要把 max、指数缩放、求和和加权累积组织成可组合的块摘要，再处理内存和数值语义。发现递归模式不等于已经推导出了它。

## 21. 可视化要让人看懂保证来自哪里

点击 Cell e-class，能看到内部 ripened egraph 和已登记的生成路径。路径可按前驱入度排序，循环用可展开的递归结构表示。

当前路径的 coarse LHS 标出触发位置；新增事实和 smooth 推导另用颜色。不能只凭最终节点就猜它由谁产生。

页面要分清：历史上观察到、结构上包含、已验证等价、可以执行的转移。我们展示的是已知路径，不是所有数学上可能的路径。

## 22. 接下来先解决什么

先修 Cell 生成中的回放和导出问题，再检查阶段信息是否贯穿提取、ripen、判等和执行。

然后选一个真实 eggcc 阶段，冻结一小组 Cell 转移，生成白名单 `.egg` 做对照。

我们要证明的不是“小 Cell 经常出现”，而是：**大 Cell 的增长主要能由少量重复的边界组合解释，而且这样执行确实更便宜。**
