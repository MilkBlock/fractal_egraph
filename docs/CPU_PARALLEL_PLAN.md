# minimal Cell CPU 多线程实施计划

以 `d4074488` 的独立 Cell CPU 为基线。目标是降低**单个程序完整推理**的耗时，保住已经省下的候选访问、稳定的 RHS 顺序和跨 Run 的 Spine 接续。第一批改动从**同一 Run、同一规则入口内的批量探测**开始。编译、离线 Bake、同时运行多个样例分别计时。

## 单线程的时间花在哪里

在 Apple M3 Max 上重新运行 minimal 验收用 release 二进制。两个 case 都使用随分支提供的 64 块 catalog。每个 case 预热一次，随后取三个独立进程的中位数。每次均核对图、调度、候选访问、Spine 接续数和最长链。以下时间单位为 ms，各阶段独立取中位数，推理总时间还包含调度等开销。[原始样本](cpu-parallel-baseline.json)

| Pass 3 | 整轮推理 | 搜索 | RHS | repair | 索引更新及发布 | 投递与 GC | 单 Run 搜索 P50 / P95 |
|---|---:|---:|---:|---:|---:|---:|---:|
| sum-bits | 30.61 | 13.05 | 6.84 | 2.13 | 4.98 | 0.43 | 0.46 / 42.58 µs |
| Raytrace | 12,071.52 | 5,176.89 | 3,169.12 | 927.14 | 2,476.29 | 290.89 | 2.71 / 1,227.54 µs |

Raytrace 的 16,883 个 Run 中，搜索达到 1 ms 的约 987 个，合计占搜索时间的 80.8%。sum-bits 的 1,428 个 Run 中，三次测量达到 1 ms 的数量中位数为零。实现中应根据**当前批次的估计工作量**派发任务；Run 的历史耗时只用于离线校准。

另用临时计时器在同一提交上跑了一次 Raytrace。其 5.399 s 搜索中，**2.790 s** 位于共享入口批次的准备、过滤、Free Join 反向筛选与准入，**0.731 s** 位于 Spine 覆盖和绑定收集，**0.754 s** 位于有寄存器计划的 pivot 循环，**0.585 s** 位于其他多原子 pivot 循环，**0.287 s** 位于最终过滤、稳定排序和去重。寄存器区间包括遍历、覆盖检查和输出，单次循环达到 250 µs 的部分合计 0.314 s。这些是含计时开销的区间；入口的 2.790 s 还包含可变缓存的创建和维护。P0 要先测出其中可独立执行的部分。[区间数据](cpu-parallel-baseline.json) · [当前匹配流程](../engine/cell-runtime/src/runtime.rs)

**2× 的预算。** 用各次实测的阶段占比代入 `S(p) = 1 / ((1 − f) + f/p)`。即使整个搜索都能均分且并发无开销，Raytrace 的整轮上限也只有 4 线程 **1.47×**、16 线程 **1.67×**。把整个索引更新及发布也计入，4 线程上限约 **1.90×**。4 线程要达到整轮 2×，理想情况下至少要覆盖总时间的三分之二，实际还需支付准备、汇合和内存访问成本。

**原生对照。** 用 eggcc 锁定的 egglog 内核 `ebba7bb` 执行原始、未加 marker 的 sum-bits Pass 3，先完成初始化，再从首条 RunSchedule 开始计时。每次新建进程，设置并核实实际池大小，每档预热一次、交错测五次。1 / 4 / 16 线程中位数分别为 **41.54 / 47.23 / 57.57 ms**，相对单线程为 **1.00 / 0.88 / 0.72×**。各次的四个抽查表大小一致。此前提到的 1.3× 在这个固定输入、版本和机器上没有复现。EggFuse 的并行扩展性需要自己的实测曲线；原生对照只用于观察小负载的调度成本。[样本及输入版本](cpu-parallel-baseline.json)

## 并发边界

每次 Run 从已修复的图上取匹配，按源规则列表构造有序 `StagePatch`，再依次 apply、repair、发布并投递到下一轮。协调线程持有 epoch、每条规则的 watermark、dirty/pending、Cell ID 和获胜的 cursor。工作线程只处理一个封存快照上的局部计算，任务结束后由协调线程接收结果。[Run 主循环](../engine/cell-runtime/src/runtime.rs)

- **顺序及归属。** 任务携带源规则序号、pivot、原 seed 序号和域内顺序。继续使用现有 `(epoch, witness)` 比较和相等时的 atom 顺序。先恢复串行候选生成顺序，再按原 input 槽顺序稳定去重。工作线程完成先后不能改变胜出的 witness、生产者引用或 Cell ID。[寄存器内核](../engine/cell-runtime/src/execute_kernel.rs)
- **Spine。** 已覆盖的单位是 `(atom, witness)`。完整覆盖的规则可直接返回；混合覆盖的规则只派发未覆盖入口。原实现按 witness、atom 给路由排序，同一绑定选较深 cursor，等深保留先到者。协调线程执行这一归约，保存 `origins` 和整条规则的 `complete` 判定；批次切片需继承该判定。真实 RHS 应用后才推进接续。[Spine 路由与归约](../engine/cell-runtime/src/stage_spine.rs)
- **共享数据。** 逻辑快照期间，入口刷新、Free Join 和邻居读取仍会写缓存。现有 `Rc<Packet>`、`Rc<Vec<Dependency>>`、`Cell<u64>` 计数器和 Spine 的 `OnceCell<RefCell<Context>>` 都有具体所有者。协调线程持有其生命周期，向 scoped worker 借出不可变的值切片、域切片和版本号。worker 返回局部结果与计数。试点必须通过 Rust 的 Send/Sync 检查，并记录为形成这些只读视图实际复制的字节数。[共享入口](../engine/cell-runtime/src/entry_schedule.rs) · [邻居上下文](../engine/cell-runtime/src/neighbor.rs)

## 实现顺序与合并条件

| 阶段 | 实现 | 进入下一阶段的条件 |
|---|---|---|
| **P0　测可拆工作** | 在诊断构建中把入口时间再拆成共享节点刷新、反向筛选、缓存命中、缺失键建域、参数打包。按 Run / 规则 / pivot 记录 seed 数、不同投影键数、域长度分布、重键、Spine 覆盖率和输出量。测常驻线程池派发加汇合的延迟。用现有执行顺序重放任务划分。 | 给出 Raytrace 各区间可拆时间占比与 4 线程上限，列出最重批次及准备成本。若候选入口不足整轮约 12%，即使理想四等分也达不到整轮 1.10×，应先换区间或合并评估 P2。 |
| **P1　并行入口准入** | 先在一个规则的一个 pivot 上工作。协调线程刷新本次所需节点、完成 Sieve/Spine 归属检查，准备必要索引。按投影和键分组，对同一版本的重复探测只建一次域；工作线程处理独立键组的只读筛选和域探测，结果按原 seed 序号回填。多阶段准入保留原先短路次序。冷索引和难以借出的域先走串行。 | 一线程与 minimal 对齐；并行批次的总耗时包含准备、拷贝、排队和汇合后低于串行。小批次旁路在线程池唤醒之前完成。此时 RHS 和 repair 仍由协调线程执行。 |
| **P2　同一批里的残余寄存器匹配** | 重用 P1 的快照和域，每个 worker 独占寄存器、scratch、绑定输出和计数。先做 `Get`、`Concat` 等已具备通用计划的形状。按预计父行访问数切块；单个重键可以切分其稳定有序的父行范围。协调线程持有兄弟属性槽与邻居组，先支持命中项，冷槽位以显式准备或串行回退处理。首版 Spine 继续承担其已覆盖的 `Single` 入口。 | 核对共享域建立次数、重复父行解码、候选访问和获胜 Spine 树。将按表达式键分组与同等工作量的连续切块对比，以每千次访问的缓存缺失、复制字节、worker 忙时及最长任务验证局部性收益。 |
| **P3　分表更新索引和发布** | 对 repair 后的 coalesced changes 先按表分组，保留旧/新键、删除、可见性、同键替换及 receipt 转发。每个表的索引和邻居订阅交给同一所有者。先处理互不相依的表。热点表再考虑按键分片，同一旧/新键关联的事件按一致顺序交付。维持 Spine、共享入口、range、查询索引/邻居、Sieve 和下一 Run 投递之间现有的可见性边界。 | 单独测“分组 + 更新 + 发布 + 同步”，包括重复解码和索引内存。覆盖缺失键后到、删除重插、两个发布顺序及 union 改键。下一 Run 只能读取完整的新版本。 |
| **P4　按收益扩大写侧覆盖** | 对尚占主导的部分再选一条路线。可先并行计算只依赖已封存输入槽的纯 RHS 算术，协调线程按原顺序核对并执行写入、merge、ID 分配和生产者登记。对 repair，先试并行发现受影响行或生成修复建议，再串行验证和应用。涉及动态函数读、过期 receipt、跨表 merge 或新增 union 的任务保留顺序处理。 | 只有前几阶段的实测上限仍低于目标且该区间有足够独立工作，才投入此阶段。进入并发提交前，另行证明冲突检测、分配顺序和跨分片的同余闭包。 |

编译器已有 `row_kernel::Kernel`、完整键/扩展步骤、邻居槽位、单写入 RHS 和 Spine 计划。先从这些描述派生任务边界。只有运行时无法廉价恢复的信息才扩展可选 artifact 字段，旧产物由相同 IR 派生。迭代 Bake 决定可切换的指令块；一次目录命中仍需对应本轮的可见事实和有效端口。训练和带审计的重放先保留固定顺序。[寄存器计划](../engine/cell-runtime/src/row_kernel.rs) · [迭代 Bake](../engine/cell-runtime/src/iterative.rs)

## 线程数、验收与停止条件

- **一个公开参数。** 建议给 `cargo cell-run` 和 `cargo cell-bench` 增加 `--threads N`，默认 1，N 包含参与计算的协调线程。每个执行器复用一个有上限的池。小批次直接调用当前串行入口。初始派发门槛用实测派发与汇合成本校准；同时要求有多个独立工作块，并把高扇出的单键拆到足以负载均衡的大小。线程数、退回串行的批次数和实际 worker 忙时写入报告。
- **正确性门槛。** 在 1/2/4/8/12/16 线程、不同切块和扰动完成顺序下，Raytrace 的 16,883 个 Run 与 sum-bits 的 1,428 个 Run 均逐字节比较有序 RHS digest；核对调度、最终图、事实与更新/union 数、完整获胜 Spine 前缀树。接续数/深度应分别为 663,403/29 和 3,034/12。对顺序敏感 merge、强制哈希碰撞、重复 pivot、等深 Spine、删除重插及超高扇出另设小型反例。任何不一致先阻止合并。
- **工作量门槛。** 固定目录的候选访问分别为 7,263,030 和 19,154。只并发化原算法时应相等。若算法同时减少访问，单独提供一线程消融。分别计复制字节、缓存填充、上下文维护、候选与输出绑定，避免把查询成本转移到汇合或发布。
- **性能门槛（提议）。** 用同机 release、同一 artifact、独立进程，预热后交错计时；Raytrace 至少 5 个配对，sum-bits 至少 9 个。比较冻结 minimal 一线程、新实现一线程及各线程数，公布单样本、配对差、整轮推理、CLI、各阶段耗时及峰值 RSS。初始合并线可取新一线程回退不超过 3%、sum-bits 自动旁路回退不超过 5%、P1+P2 的 Raytrace 四线程整轮至少 1.10× 且多数配对更快；接近噪声边界就扩大样本。记录 12 个性能核与 4 个能效核的机器拓扑。16 线程持平或退化时检查重键、缓存重复、带宽和等待，再决定最佳默认值。
- **第一份可评审交付物。** P0 的可拆比例、派发开销、模拟分块最大负载和单线程重放摘要；随后一个只覆盖热入口的 P1 原型。是否扩展到 P2/P3，由每项对完整推理的收益决定。
